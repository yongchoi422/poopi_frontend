# SOULI 개인 대기방 제작안 · My little room

2026-10-04. 사용자가 기존 `게임 기획 모아 분석하기` 스레드에서 대기방을 진행하도록 요청했다. 이 문서는 게임 제작 범위와 웹 통합 경계를 정한다. 제안한 방 테마가 이미 출시됐거나 구매 권리로 보장된다는 뜻은 아니다.

## 목적과 첫 결과물

구매자가 원본 inscription을 보며 “내 소울이 여기 쉬고 있구나”를 느끼는 작은 개인 공간. 이름은 **My little room**을 기본으로 한다. 별도의 로그인 대기열, 자산 예치 또는 보상 대기 상태가 아니다. 먼저 **잘 다듬은 방 하나 + 소울 하나 + 자동 행동 세 종류 + 사진 저장**을 완성한다. 웹 판매/지갑 코드는 현재 홈페이지 스레드에서 통합한다.

정식 게임의 전투·멀티플레이·성장 규칙이 바뀌어도 이 공간은 계속 쓸 수 있어야 한다. 재방문을 압박하는 배고픔, 죽음, 출석 손실, 토큰 보상은 이번 범위에 없다. 구매할 때마다 별도 캐릭터가 생기는 구조라고 가정하지 않는다. 실제 지갑의 Dynamic/Stable inscription 선택을 입력받는다.

## 방 아이디어와 구현 순서

| 공간 | 인상과 소품 | 소울의 작은 행동 | 범위 |
|---|---|---|---|
| **Little Daylight** | 하얀 미니어처 방, 큰 창, 옅은 나무 탁자, 파란 쿠션, 금색 스탠드 | 둥둥 쉬기, 창가 보기, 쿠션에 기대기 | 첫 출시용으로 구현 |
| **Rainy Window** | 같은 방, 창밖 비, 따뜻한 조명, 작은 머그 | 창을 구경하다 돌아오기, 머그 옆에서 쉬기 | 같은 모델의 후속 조명·소품 변형으로 설계만 우선 |
| **Tiny Workshop** | 같은 방, 작은 책상, 돌 하나, 종이 한 장 | 돌을 놓고 관찰하기, 종이에 작은 흔적 남기기 | 정식 게임의 수집/작업 감정으로 이어질 후속 안 |

과금·토큰 잔액에 따른 방 잠금은 도입하지 않는다. 다양한 형태와 색상의 원본을 배치했을 때 잘 보이는 것이 우선이다. 첫 버전 방 선택 메뉴는 하나뿐인 콘텐츠를 불필요하게 감싸지 않는다. 후속 테마까지 당장 모두 만들 필요는 없다.

## 시각과 행동

- 기존 `output/game/room-v2/model.mjs`, `soul-volume.mjs`, `preview.mjs`와 하얀 미니어처 세계의 결과를 먼저 확인하고 재사용한다. 기존 실험 파일은 보존한다.
- 크림·밝은 흰색 배경, 파란색과 금색 소품을 적게 쓴다. 원본 소울의 앞면 픽셀·실루엣·색이 중심이다. 옆면/그림자로 두께를 표현하되 뒷면에 새 얼굴을 만들지 않는다.
- 카메라는 기본 시점을 고정하고 캐릭터가 작아지지 않게 잡는다. 모바일에서 방 전체를 억지로 축소하지 않고 주요 가구와 소울이 함께 보이게 구성한다.
- Level1 dot도 바닥에 묻히지 않도록 캐릭터의 화면상 최소 크기와 명암을 보장한다. 장식 빛·그림자는 표현 효과이며 원본 inscription의 진화나 새로운 픽셀로 설명하지 않는다.
- 입장 후 클릭 없이 동작한다. 느린 부유/휴식, 짧은 자리 이동, 소품 옆 작은 반응의 세 종류를 반복한다. 몸이 없는 dot에게 팔다리를 임의로 붙이지 않는다.
- 방은 20–40초 관찰하면 작은 변화가 한 번 보이되 상시 흔들림/입자를 과하게 쓰지 않는다. 사용자 조작은 가까이 보기와 사진 저장 정도. 숨겨진 탭은 렌더를 멈추고 reduced-motion/Still을 제공한다.
- 화면 영어는 `My little room`, `Take a photo`, `View original`, `Still` 정도로 짧게. 세계관 장문, 통계판, 퀘스트, 통화/보상 숫자는 넣지 않는다.

## 접속·소유권·저장

- 비보유자/미연결 미리보기는 **Sample soul**을 명시한다. 이것을 구매자의 소유 캐릭터라고 보여주지 않는다.
- 지갑 연결·네트워크 확인·원본 조회는 웹 담당이 제공한다. 현재 `src/soul/inscription.mjs`의 `readOwnedSouls`는 `svg, seed, extra, level, dynamic, owner, block, source`를 반환한다. 연결 데이터가 바뀌면 렌더러가 기존 모델을 폐기하고 새 모델로 바꿀 수 있어야 한다.
- 지갑/네트워크 변경, disconnect, 조회 실패 때 오래된 소울을 현재 소유물로 계속 표시하지 않는다. 로딩/빈 결과/실패/샘플/보유자/소유 여러 개 상태를 명시적으로 입력받는다.
- 3D는 원본의 파생 표시다. 새 NFT, on-chain3D, 토큰 전송/잠금/스테이킹을 추가하지 않는다. 구매 승인과 방의 시각 상태는 별개다.
- 브라우저 내 움직임/시각 설정만 필요하다. 기본 생활 동작에 서버나 트랜잭션은 없다. 탭을 닫은 동안 서버가 계속 돌았다고 주장하지 않는다. 외부3D생성API/유료서비스/전용DB를 도입하지 않는다.
- 사진은 장면+SOULI 작은 브랜딩으로 저장. 주소/잔액은 기본 제외. 샘플이면 공유 결과에도 Sample 표시. 원본 공유 기능은 웹 담당이 연결한다. 사진은 PNG 다운로드부터 확인하고 모바일 Web Share는 지원할 때만 사용한다. SNS 자동 게시 없음.

## 작업 파일 경계와 통합 계약

- 게임 담당 작업 경로: **`output/game/waiting-room/`**. 독립 로컬 프리뷰, 재사용 가능한 렌더 모듈, 전용README/검증 결과를 만든다. 필요하면 기존room-v2에서 게임용 소스를 복사하거나 그대로 참조하되 원본 실험은 수정하지 않는다.
- 현재 웹 담당 소유: `src/site`, `src/buy`, `src/soul`, `src/lighthouse`의 공유 지갑/결제, `src/sale-admin`, `contracts`, 루트package/lockfile/vite, 공개배포. 게임 담당은 이 파일들을 변경하지 않는다. 공유 HANDOFF도 동시 수정하지 않고 게임 전용README에 기록한다.
- 렌더 모듈은 DOM container와 검증된 원본/screen state를 입력받고 setSoul/setState, pause/resume, capture, dispose에 해당하는 API를 제공한다. Vue 또는 지갑 SDK를 직접 소유하지 않는다. 외부에서 현재 소울을 주입하여 샘플을 하드코딩하지 않고 바꿀 수 있어야 한다.
- 초기 프리뷰에는 기존 공개 샘플과 실제 `readOwnedSouls`와 같은 모양의 fixture를 쓴다. 이 단계는 실제 지갑 연결 완료로 표시하지 않는다. 홈페이지 담당이 이후 검증된 원본조회와 연결한다.
- 임의 SVG를 innerHTML로 삽입하지 않는다. 기존 원본 허용 형식에 맞춘 검증과 크기 상한을 적용한다. 지원하지 않는 그림은 그럴듯하게 새로 만들지 않고 원본2D fallback을 제공한다.
- 배포용 결과는 추후 웹프로젝트의 정적/번들 경로로 옮긴다. output 로컬URL/Drive 링크를 production src로 쓰지 않는다. 이번 게임 스레드는 로컬 제작·검증까지만 하고 공개 배포는 웹 담당이 한다.

## 완료 기준

1. 320/390/1440px에서 방·소울·주요 버튼이 보이고 가로 넘침이 없다.
2. dot, 밝은/어두운 소울, 분리 이펙트 픽셀, 큰 형상에서 실루엣·앞면을 보존한다.
3. 샘플→보유데이터fixture→다른소울→disconnect/실패 전환 시 이전 소울이 남지 않는다. 여러 번 전환/dispose 후 GPU 리소스가 누적되지 않는다.
4. 별도 클릭 없이 생활동작, Still/reduced-motion, 탭 숨김 중 정지, WebGL없음/생성실패 시2Dfallback을 확인한다.
5. 사진 저장이 실제로 작동하고 sample 표시와 개인정보 제외를 확인한다.
6. 게임서버/지갑서명/토큰전송 없이 동작하고, 실제기기에서 확인하지 않은 성능을 테스트 완료로 주장하지 않는다. 목표는 30fps/DPR상한1.5 정도이며 실제 측정과 목표를 구분한다.
7. 실행주소, 수정파일, 재사용한 원본, 입력/출력API, 완료/미완료, 검증스크린샷을 게임 스레드 최종 결과와 전용README에 남긴다.

다음 통합 목표는 **구매 확인 → 현재 inscription 조회 → 내 방 보기**다. 방이 공개 검증되기 전 홈페이지에는 계속 Cooking으로 표시한다.
