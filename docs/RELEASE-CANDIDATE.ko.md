# SOULI 출시 후보 1.4 — 실제 검증과 남은 단계

2026-09-30. 이 문서는 이전 인수인계의 오래된 검증 상태보다 우선한다.
**로컬 출시 후보이며, 운영 배포 또는 실제 판매 개방은 하지 않았다.**

1.4의 요청 시 정산·5분 체크포인트·Firestore 옵션·검증과 Docker 설치 상태는 [저비용 실행 구조](LOW-COST-RUNTIME.ko.md)가 최신이다. 최신 검증은 프런트 8개/서버 23개/build/격리 import, 실제 PostgreSQL 13개+재시작, 공식 Firestore 에뮬레이터 14개 통과다. 아래 구현 목록·크기 수치는 1.3 검증도 포함한다.

## 구현과 검증

- 자동 생활·ETH 날씨·비동기 협동·원본 SVG와 점 형태를 유지했다.
- Vite 4 → 7.3.6, Vue 3.5.43, 플러그인 6.0.9로 갱신했다. 빌드 도구는 개발·빌드 전용이고, 운영은 Node 24가 `dist`와 API를 같은 origin에서 제공한다. `vite --host`나 `vite preview`를 운영 서버로 쓰지 않는다.
- 새 클라이언트는 ethers 6.17.0을 주소 조회 시에만 불러온다. 기존 약 1.417MB 게임 JS에서 최초 진입용 게임+공유 JS 약 153KB, gzip 약 53.5KB로 줄었다. 추가 RPC 모듈은 256KB/gzip 95.9KB이며 최초 진입에는 필요 없다. CSS·폰트는 별도다.
- npm lock을 갱신하고 `npm ci` 후 재빌드했다. 새 루트 의존성 전체 및 서버 운영 의존성의 npm audit 결과는 0건이다. 전체 애플리케이션 보안 감사를 뜻하지 않는다.
- Windows 정책이 Rollup 네이티브 모듈을 차단하여 공식 `@rollup/wasm-node` 4.63.5로 빌드한다. 보안 정책을 해제하지 않았다. [Rollup 공식 설명](https://github.com/rollup/rollup/blob/master/ARCHITECTURE.md).
- 원래 수집 앱의 의존성/잠금은 `legacy/`에 보관했다. 기존 소스와 저장은 유지했다. 새 운영 빌드에서 옛 Web3/wagmi/WalletConnect를 설치하거나 포함하지 않는다. 기존 프로필의 알려진 취약점은 해결됐다는 뜻이 아니다.
- EIP-6963 지갑 탐색, 이미 허용한 주소의 조용한 복원, 연결한 바로 그 provider를 이용한 로그인 서명을 연결했다. 브라우저 새로고침 시 같은 지갑의 유효한 서버 세션이면 집을 다시 연다. 자동 서명이나 결제는 없다.
- SIWE challenge를 HttpOnly 쿠키로 요청 브라우저에 묶었다. 서명 재사용·위조·만료·다른 브라우저·다른 origin과 잘못된 JSON을 거부한다. EOA만 지원하며 스마트 계정 지원을 주장하지 않는다.
- 일시적인 서버 연결 실패는 재연결 상태를 표시한다. 1.4부터 화면은 마지막 서버 체크포인트와 확인된 2시간 참여 시한 안에서 로컬 표시만 진행하며, 그 값을 서버 보상으로 제출하지 않는다. 협동 기여·결과는 서버 확인값을 유지한다. 세션 만료·보유 조건 실패는 별도 로컬 저장으로 돌아간다.
- CSP, 보안 헤더, 정적 HEAD, 해시 자산 캐시, 요청 식별자, 장애 시 비공개 정보가 없는 오류 응답을 추가했다. 쓰기와 쿠키 API의 교차 사이트 접근을 거부한다.
- `/api/health/live`는 프로세스, `/api/health/ready`는 DB 연결을 검사한다. Base/시장 피드 상태까지 보장하지 않는다. `/api/status`의 `sales`는 계속 false다.
- Docker 런타임에 누락됐던 `market-world.mjs`를 포함했다. Dockerfile의 실제 COPY 목록만 격리 폴더에 복사하여 서버 모듈 import를 검증한다. **이는 Docker 이미지 실행 검증과 다르다.**
- 1.4에서는 공개 시장 조회를 영속 5분 캐시로 공유하고 집/동네 전체 순회를 없앴다. 게임 상태는 요청한 동네만 서버 시간과 트랜잭션으로 정산한다.

`npm test`: 프런트 로직 스크립트 7개, 서버·규칙·HTTP 테스트 19개, production build, 격리 패키지 검사를 통과했다. 기존 4개 테스트도 포함한다.

별도 PostgreSQL 18.4를 loopback과 임시 무작위 인증정보로 실행했다. Windows 서비스나 OS 사용자를 만들지 않았다. PostgreSQL 경로의 API 회귀 묶음 13개(그중 SQLite 전용 1개 및 설정 검증 포함), 동시 기여·두 지갑 분리·서명·이벤트 복구를 통과했다. DB 프로세스를 실제 중지/재시작하여 커밋된 저장이 유지되는 것도 확인했다. 테스트 클러스터는 종료되며 데이터/로그만 Git 제외 `logs/pg-check-*`에 남는다. **운영 백업에서 복원하는 재해 복구 검증은 별도로 남아 있다.**

빌드된 4173 화면에서 실제 Base 공개 주소의 원본 SVG와 L4 메타데이터 조회, 390px 모바일 넘침 없음, 이미지 로드, 지갑 미설치 안내, 구매 비활성 문구를 확인했다. 브라우저 콘솔 오류는 없었다. 테스트 주소 조회는 소유 인증이나 해당 지갑의 서명을 뜻하지 않는다. 실서비스 사용자는 실제 MetaMask에서 서명해야 한다.

## 실행

```powershell
npm.cmd ci
npm.cmd ci --prefix server
npm.cmd test
# 각각 별도 터미널
npm.cmd run dev:api
npm.cmd run dev -- --host 127.0.0.1 --strictPort
```

게임: `http://127.0.0.1:5173/lighthouse.html`.
빌드 UI 검토: `npm.cmd run preview -- --host 127.0.0.1 --port 4173`.
4173은 다른 origin의 별도 로컬 저장이며, 기본 5173 SIWE 서명 테스트용 주소가 아니다.

기존 수집 앱 유지보수: `npm.cmd ci --prefix legacy --ignore-scripts`, `npm.cmd run dev:legacy -- --host 127.0.0.1 --port 5174`; `/legacy.html`을 연다. 운영 프로필로 사용하지 않는다.

선택 Windows 실제 PostgreSQL 회귀 테스트:

```powershell
npm.cmd install --prefix logs/pg-runtime --no-audit --no-fund embedded-postgres@18.4.0-beta.17
npm.cmd run test:postgres
```

별도 DB 환경에서 직접 API 테스트를 실행할 때는 `SOULI_TEST_DATABASE_URL`에 **폐기 가능한 `souli_test_` 접두사 DB만** 지정한다. 테스트가 독립 스키마를 생성·제거한다. 운영 DB URL을 넣지 않는다.

## 출시 전 실제로 남은 것

1. Docker 이미지 빌드·기동·healthcheck 검증. Docker Desktop, WSL 3.0.1, Windows Virtual Machine Platform 설치가 완료됐다. Windows의 재부팅 필요 상태(DISM 3010, RebootPending)를 확인했으므로 재부팅 후 Docker Desktop을 시작하고 `npm run test:docker`로 격리 검사를 실행한다. 설치 완료가 이미지 실행 검증을 뜻하지 않는다.
2. 운영 Firestore의 IAM/색인/백업 복원 또는 기존 PostgreSQL의 TLS/권한/백업 검증. 실제 저장소 전환은 하지 않았고 설정 변경만으로 데이터가 옮겨지지 않는다.
3. 실제 HTTPS beta origin·허용 지갑·운영 RPC 설정. 프록시는 Origin/Cookie를 유지한다. X-Forwarded-For를 임의로 신뢰하지 않으며 현재 제한은 소켓 IP별 분당 600회(로그인 challenge 20회)이다. 프록시 뒤 공동 IP에서는 상한이 공유되므로 작은 초대 베타부터 부하 검증한다. 다중 인스턴스 전체의 분산 rate limit은 별도다.
4. 요청 기반 Cloud Run 최소 인스턴스 0의 콜드 스타트·부하·비용 검증. 백그라운드 타이머와 전 마을 순회를 제거했으므로 게임 스케줄러가 필요 없다. SQL 경로는 기존 advisory lock을 유지하며 Firestore는 문서 트랜잭션을 쓴다. 관측하지 못한 과거 위기를 소급 생성하지 않으며 대규모 동시접속 검증은 하지 않았다.
5. 실제 MetaMask로 HTTPS 로그인 → 자동 생활 → 다른 계정/네트워크 → 만료 → 재로그인. 내장 브라우저에는 확장이 없어 이 단계는 완료하지 못했다.
6. 기존 Cloud Run `pickit-lab/souli/us-central1`의 현재 이미지·환경·DB/트래픽 경로를 검토하고 이전 revision과 DB 스냅샷을 보관한 뒤 수동 배포. Azure 이전은 보류다. 이번 작업에서 배포·DNS·계정 권한을 변경하지 않았다.

실제 판매는 별도의 계약·경제 조건·Base fork 테스트·검토가 필요한 단계다. `PURCHASE.saleContract=null`과 서버 `sales=false`를 유지한다. 미확정 $15M FDV/100% LP 제안은 홈페이지와 운영 구매 화면에서 제거했고 개발용 시뮬레이션 소스는 보존했다.

## 사용자 지갑과 판매 연결안 — 미확정 제안

기존 보유자의 게임 입주는 SOULI 계약을 읽고 지갑 서명을 검증하는 방식이다. 토큰을 게임 서버나 개발자 지갑으로 보내지 않는다. 서버에 개인키/시드 구문이 필요하지 않다.

새 판매 계약을 선택하면 소유자가 MetaMask로 **판매용 SOULI와 LP 짝맞춤용 SOULI를 계약에 입고**한다. 입고 수량·계약 주소·회수 가능 조건을 먼저 검토하고 실제 거래는 본인이 승인한다. 판매대금·LP를 개인 지갑에 임시 보관하는 대신 계약이 검증 가능한 규칙으로 관리하도록 설계하는 것을 권한다.

현 시점 권장안은 **고정가 예약 판매 → 목표 달성 시 LP 생성 → SOULI 수령**, 목표 미달/기한 종료 시 환불이다. 환불을 보장할 예약 기간에는 구매자 SOULI와 자금 모두 계약에서 보관한다. 기존 토큰을 즉시 지갑에 지급하고 자유롭게 이전할 수 있게 하면서 무조건 전액 환불도 제공한다고 약속하지 않는다. 즉시 SVG 소유·거래가 우선이면 먼저 초기 LP를 마련하고 기존 AMM 매수를 연결하는 대안이 있다.

LP는 모은 현금만 보관하는 곳이 아니다. 같은 풀에 SOULI와 USDC/ETH 두 자산을 함께 넣고 LP 소유권·수수료·출금/잠금 권한을 정한다. 판매 단가와 풀 초기 단가가 같고 수수료를 무시하면, 구매자 물량 Q와 판매대금 중 LP 비율 L에 대해 별도 LP용 SOULI는 L×Q, 총 입고는 Q×(1+L)이다. 이는 설명용 관계이며 판매 배분을 확정한 수치가 아니다. [Uniswap 풀 구조](https://docs.uniswap.org/whitepaper.pdf).

Pump.fun의 곡선은 매수 시 상승·매도 시 하락하고 정해진 조건에서 풀로 이전하는 구조다. 상승 보장 장치가 아니다. 기존 투자자와 팀이 이미 보유한 SOULI 물량까지 새 곡선에 매도할 수 있다면 외부 유통량과 준비금의 관계를 검증해야 한다. 새 토큰의 발행·회수 모델을 기존 ERC20i에 그대로 적용하지 않는다. 초기에는 이 복잡성을 더하지 않는 것을 권한다. [Pump 공식 설명](https://pump.fun/docs/bonding-curve).

기존 판매대금은 이미 사용되었다는 사용자 설명을 전제로 운영비를 0으로 잡지 않는다. 공개한 운영비 몫 또는 별도 운영자금과 LP 자금을 분리하고, 정확한 비율은 비용표와 함께 결정한다. 100% LP와 운영비 사용을 동시에 약속하지 않는다. 팀 토큰 매도만으로 서버비를 충당하는 방식은 시장 하락 때 운영까지 흔들릴 수 있다.

아직 미정: USDC/ETH 선택, 가격, 판매량, 최소 목표/상한/기한, 운영비 배분, LP 풀·잠금·수수료 귀속, 팀 잔여 물량 정책. ERC20i 실제 전송/원본 변화와 기존 풀 상태를 Base fork에서 검증한 뒤 견적·승인·입고·영수증 흐름을 연결한다. 이 문서만으로 판매 조건이 확정되거나 스마트 계약이 배포된 것은 아니다.
