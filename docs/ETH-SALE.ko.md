# SOULI Base ETH 판매 — 구현과 운영 준비

## 최신 관리 권한 (2026-10-02)

Safe 대신 [세 지갑 개별 관리 controller](THREE-WALLET.ko.md)를 추가한다. 기존 SouliEthSale의 owner/treasury를 controller로 지정하고, 세 운영자가 각각 단독 호출한다. 기존 EOA 테스트 판매의 immutable treasury를 바꾸는 것은 아니다. 메인넷 판매는 계속 비활성.


기준: 2026-10-02. 게임 장르 변경과 독립적으로 사용할 수 있는 **재고 입고 → ETH 결제 → SOULI 즉시 지급** 경로를 구현했다. Base Sepolia에서 실제 MetaMask 배포·구매·재고 회수/재입금·판매대금 인출의 기본 흐름을 완료했다. [테스트 거래와 정확한 범위](TESTNET.ko.md)를 따른다. **메인넷 배포·실자금 입고·실판매는 수행하지 않았고** `LIVE_SALE.enabled`는 `false`다. 아래 검토는 독립 보안 감사를 뜻하지 않는다.

## 최신 결정 — 수동 LP, Safe는 2-of-3

사용자가 자동 LP를 중단하고 기존 `SouliEthSale`처럼 treasury로 판매대금을 인출한 뒤 운영자가 Uniswap에 수동 공급하는 방향을 선택했다. [현재 수동 LP 운영 규칙](MANUAL-LP.ko.md)이 아래 과거 LP 전용 계획보다 우선한다. 즉시 지급은 유지하고 초기 판매금의 LP 사용은 운영 의도이며 계약상 강제가 아니다. 사용자는 1-of-3 검토 후 **A/B/C 중 두 지갑이 승인하는 2-of-3으로 확정**했다. 실제 Safe는 미구성이다. 두 서명자는 전액 이동과 승인 규칙 변경이 가능하므로 LP 잠금과는 다르다. 계약/실제 지갑/공개 사이트 변경은 없고 LP 전용 후보는 연구 기록으로 보존한다.

## 과거 계획 — 즉시 지급과 LP 전용 적립 (수동 LP 결정으로 대체)

최신 추가: 별도 `SouliLpSale`/`SouliPermanentLpLock` **후보 구현**과 새 LP 실패 검증 27개, 기존 포함 68개 회귀 테스트, 실제 Base 포크 9개 경로를 통과했다. [LP 후보 검증 기록](LP-SALE-VALIDATION.ko.md)이 아래 과거 미구현 문구보다 우선한다. 새 공개 배포·실제 Safe·LP 구매 UI·자동 실행기는 아직 없으며 기존 Sepolia treasury 계약은 교체하지 않았다. 영구 잠금·추가 SOULI 준비분·기존 풀의 장기 가격 이탈 시 지연은 최종 출시 조건 검토 대상이다.

추가 사용자 기준: **FDV 15M USD, ETH 쪽 50k USD 상당 + 맞은편 SOULI**. 이는 기준 달러 계산이며 실제 ETH/wei·잠금·기간 조건은 미확정이다. [토크노믹스 제안과 운영자금/원본 단계 분석](SOULI-TOKENOMICS.ko.md)을 함께 읽는다. 기존 투자자 지급량은 확인 중이다.

**이 절은 다음 버전의 요구사항이며 공개 출시 완료 보고가 아니다.** 사용자는 LP 생성 뒤 토큰을 청구하는 예약 판매와 목표 미달 환불을 원하지 않는다. 구매 즉시 받은 SOULI로 게임을 이용하고, 새 초기 판매대금은 전액 LP에만 쓰는 구조를 선택했다. 아래 기존 계약의 treasury 인출 설명은 현재 공개 테스트한 버전의 동작이며, 새 LP 전용 계약의 권한으로 그대로 이어지지 않는다. 기존 41개 테스트 통과만을 새 LP 설계의 검증 결과로 쓰지 않는다.

### 자산 흐름과 권한

```text
구매자 Base ETH ── 구매 계약 ── SOULI 즉시 지급 ── 보유 확인 후 게임
                       └───── 결제 ETH 전액 → LP 전용 적립
창업자/다른 참여자 ── LP 지원 입금 ──────────┘
판매 시작 전 별도 확보한 LP용 SOULI ──────────┐
                                          ↓
                         목표 충족 → 정해진 Uniswap 풀에 공급
                                          ↓
                         LP 소유권을 정해진 잠금 주소로 직접 지급
```

- **지급 실패는 결제 실패다.** SOULI 지급 또는 LP 적립이 실패하면 해당 구매의 ETH·토큰·집계 전체를 되돌린다. 이는 성공한 구매를 나중에 환불하는 기능과 다르며 실패 거래의 네트워크 가스비는 남을 수 있다.
- 구매 재고와 LP용 SOULI를 분리하고, 목표 전액에 대응하는 LP용 수량을 **판매 시작 전에** 확보·검증한다. 나중에 운영자가 넣어 주겠다는 약속만으로 판매를 열지 않는다. LP 지원자는 SOULI·LP 지분·개별 인출권을 자동으로 받지 않는다. 같은 조건으로 SOULI를 받고 싶으면 일반 구매를 이용한다.
- 구매 ETH/지원 ETH/준비 SOULI에는 관리자 인출·임의 수령지 변경·임의 외부 호출·업그레이드를 통한 우회 출금 경로를 두지 않는 것을 설계 불변조건으로 삼는다. **Safe 2-of-3도 LP 전용 자금이나 잠긴 LP를 꺼낼 수 없어야 한다.** 별도 운영비 금고와 구분한다.
- 신규 구매 중지와 **미판매 구매 재고** 회수는 운영 Safe 권한으로 검토하되 LP 준비 재고·기지급 구매자 토큰·LP 자금은 회수 대상에서 제외한다. 동일 토큰이라도 회계상 분리만으로 끝내지 않고 잔액/권한 테스트로 강제한다.
- 목표 미달 시 구매자는 이미 SOULI를 가진 채 게임을 이용하고, 적립 ETH는 LP 용도로 남는다. 목표 달성이나 LP 생성 시점, 재판매 가능성은 보장하지 않는다. 영구적으로 미달하거나 복구 불가능한 계약/DEX 문제가 생기면 LP 자금이 무기한 잠길 수 있다는 점을 구매 전에 짧게 고지한다. 환불 함수가 없다는 것은 계약 기능 설명이며 모든 판매 지역의 법적 권리까지 없어진다는 뜻으로 쓰지 않는다.
- 100%는 **구매대금 원금** 기준이다. 가스·서버·감사·실행기 비용을 이 적립금에서 공제하지 않는다. LP에서 발생할 거래 수수료의 권리/수령 가능성은 선택한 DEX와 잠금 방식에 따라 별도 확정하며, 기존 모금액을 운영 수익이라고 표시하지 않는다.

### Uniswap 자동 연결 제안

Pump.fun에서 참고하는 경험은 목표 진행률과 목표 도달 후 거래 풀로 이어지는 흐름이다. Pump.fun은 졸업 전에도 매수·매도가 가능한 본딩 커브를 사용하고 PumpSwap으로 이동한다. **SOULI의 제안은 즉시 지급 고정가 판매 + LP 전용 적립 + Base의 Uniswap 연결**이며, 본딩 커브 매도·환매·자동 가격 상승을 구현했다고 설명하지 않는다. [Pump 공식 구조](https://pump.fun/docs/bonding-curve)

권장 상태는 `Preparing → Funding → Ready → Live`다. `Funding` 중에도 구매자는 토큰을 보유한다. 목표/준비 재고가 충족되면 `Ready`, 실제 LP 공급과 잠금이 같은 거래에서 성공한 것을 확인해야 `Live`다. 생성 시도가 실패하면 `Ready`에서 원인을 표시하고 재시도하며 구매자 토큰은 영향을 받지 않는다. 별도의 미완료 `Finalizing` 상태에 자산을 영구 고립시키지 않는다.

1. 구매와 LP 생성은 기본적으로 별도 거래로 설계한다. 목표를 채운 마지막 구매가 완료된 뒤 **권한 없는 누구나** 정해진 `finalize`를 호출할 수 있다. 호출자가 페어·수령지·가격·잠금 규칙을 임의로 고르지 못하게 한다.
2. 저비용 이벤트 감지/서버리스 실행기가 목표를 감지해 가스만 납부하고 호출하는 자동화를 검토한다. 서명용 계정에는 실행비만 두고 관리자·자금 출금 권한은 주지 않는다. 블록체인은 조건만으로 스스로 새 거래를 보내지 않으며 실행기 장애/가스 부족 시 지연될 수 있다. 누구나 지갑에서 실행할 수 있는 예비 버튼을 제공하고 자동화가 지갑 서명을 몰래 대신한다는 인상을 주지 않는다.
3. LP용 SOULI와 ETH를 검증된 라우터를 통해 공급한다. ETH/WETH 처리, 두 자산 비율, 최소 수령량·기한·정수 반올림, 가짜 라우터·선행 풀 생성·기존 가격 조작 방어를 실제 토큰 포크에서 검증한다. 불리한 기존 풀에 무조건 입금하거나 현재 풀 비율만 그대로 신뢰하지 않는다. [Uniswap 유동성 공급 지침](https://developers.uniswap.org/docs/protocols/v2/guides/providing-liquidity)
4. LP 소유권은 운영자 개인 지갑을 거치지 않고 검증된 잠금 주소에 직접 지급한다. 공급 성공/잠금 실패가 따로 남지 않게 원자적으로 검증한다. v2 LP 토큰과 v3/v4 포지션은 잠금·수수료 구조가 달라 제품 선택 전에 영구 잠금/수수료 인출을 단정하지 않는다.
5. 첫 판매가 고정가라면 `Ready`부터 새 구매/지원 입금을 닫는 것을 권장한다. 남은 목표를 넘는 입금은 수령하지 않고 전체 거래를 거절하는 경로를 검토한다. UI 견적이 오래되거나 동시 입금이 발생해도 초과분을 임의 보유하지 않는다. LP 생성 후에는 DEX 시장가와 기존 고정 판매가가 충돌하지 않게 한다.
6. 실제 공급 수량·잠긴 LP·남은 ETH/SOULI를 따로 기록한다. 라우터가 돌려주는 미사용분/반올림 잔여금도 LP 용도로 남기고 후속 처리 규칙을 확정해야 한다. 일부만 공급된 상태를 “전액 LP 투입 완료”라고 표시하지 않는다. 생성 실패/기존 풀 선점 시의 안전한 재시도 가능성을 검증하지 못하면 실판매를 열지 않는다.

기존 Base 토큰의 `pool()` 값은 DEX가 아닌 주소였고 포크에서 재설정 호출은 실패했다. 추가로 **Base 블록 52,067,385를 복제한 로컬 체인**에서 공식 Uniswap v2 라우터/팩토리로 신규 페어 생성·정확한 양쪽 공급·매수·분할 매도·원본 SVG 조회·LP 회수를 통과했다. 저장소 루트에서 `npm.cmd run test:sale:dex-fork`로 재현한다. 당시 `BASE_READ_RPC=https://mainnet.base.org`, `BASE_FORK_BLOCK=52067385`를 사용했다. 증거는 `logs/sale-checks/base-dex-fork.json`이며 공개 체인 거래는 0건이다. 원래 pool 값은 바꾸지 않았다. **새 LP 전용/잠금 계약·관리자 우회 방어·공개 테스트넷 최종 흐름은 아직 미구현/미검증**이며 이 테스트를 독립 감사로 설명하지 않는다.

### 구매 화면과 차트

메인은 SOULI 코인 로고의 파랑/금색, 원본 인스크립션, 눌리는 버튼을 유지한다. 구매 화면은 왼쪽 원본/레벨·오른쪽 수량/결제로 단순화하고 모바일은 한 열로 둔다. 차트는 선택해서 펼치는 보조 정보로 두며 게임 화면에 거래 터미널을 강제로 넣지 않는다.

| 상태 | 기본 화면 | 펼쳐 볼 증거 |
|---|---|---|
| LP 준비 중 | `Get SOULI. Play now.` + 확정 판매 단가 + `LP progress` | 판매 ETH, 지원 ETH, 목표 ETH, 남은 ETH, LP용 SOULI 준비량, 계약/거래 링크 |
| 목표 충족·생성 전 | `LP ready` / `Creating liquidity`와 확인 중인 거래 | 실행 거래/재시도 상태. 이때도 `LP live`나 잠금 완료 배지를 표시하지 않음 |
| 실제 LP 공급·잠금 확인 | `Trade SOULI` + 단순 가격선/선택형 캔들 차트 | 정확한 체인·페어, 실제 체결·거래량, LP/잠금 주소와 영수증, 상세 DEX 화면 |
| 데이터 지연/거래 없음 | `Data delayed` / `No trades yet` | 최종 갱신 시각/블록. 0 가격이나 가짜 상승 캔들로 빈 상태를 채우지 않음 |

`LP progress`는 **공식 LP를 위해 수령한 판매 ETH + 지원 ETH**를 목표와 비교한다. 판매량·매출·지원금·시가총액·풀 양쪽 가치가 서로 다른 값임을 유지한다. ETH 목표를 USD 환산하면 갱신 시각과 환산임을 표시한다. 단일 소액 거래로 크게 왜곡될 수 있는 시총 숫자나 가격 상승 표현을 핵심 구매 근거로 쓰지 않는다. 잔액 숫자만으로 100% LP 또는 잠금이 증명되지는 않으므로 검증된 코드·출금 권한·실제 LP 수령지까지 연결한다.

LP 전에는 가격 대신 시간별 **누적 LP 준비금 그래프**를 선택 제공한다. 기존 고정 판매가를 시장 캔들처럼 그리지 않는다. 풀 개설 후 DEX Screener의 정확한 Base 페어 링크/지원되는 공식 임베드, 또는 TradingView **Lightweight Charts**로 실제 거래 데이터를 표시하는 안을 검토한다. 차트 라이브러리는 시세를 공급하지 않으므로 OHLC 데이터 소스·갱신/캐시·출처 표시를 별도 검증한다. DEX Screener API의 현재 가격 스냅샷만으로 과거 캔들을 만들어 내지 않는다. 자동 색인/TradingView 종목 등록은 보장하지 않으며 외부 색인이 늦어도 온체인 풀 확인 링크는 제공한다. 초기에는 외부 차트를 선택 로드해 서버·전송 비용을 줄이고 해당 출처/CSP/개인정보 영향을 검토한다. [DEX Screener API](https://docs.dexscreener.com/api/reference), [Lightweight Charts 및 표기 조건](https://tradingview.github.io/lightweight-charts/docs)

아래는 현재 검증한 일반 treasury 인출 버전의 운영안이다. 후속 버전에서는 판매대금 Safe로의 자유 인출 대신 위 **LP 전용 적립/잠금**을 적용한다. 운영비 Safe는 별도 자금을 사용한다.

Safe는 여러 서명이 필요한 스마트 계약 지갑이고, MetaMask/하드웨어 지갑은 그 서명 수단이 된다. 위 2-of-3은 제안이지 구성 완료 사실이 아니다. 혼자 세 키를 보유해도 가능하지만 각각 독립 보관해야 하고, 여러 사람의 검토 효과까지 생기는 것은 아니다. 처음에는 임의 모듈·세션키·자동 서명·출금한도 우회 기능을 추가하지 않는다. Safe 모듈은 기본 다중 승인 밖에서 거래를 실행할 수 있다. 이 권장 구조의 실제 Safe 연결/서명/복구 흐름은 별도 검증해야 한다.

하드웨어 지갑을 사용한다면 장치에서 새 복구 문구를 만들고 오프라인으로 보관한다. 기존 브라우저 복구 문구를 장치에 넣는 것만으로 과거 노출 위험이 없어지지 않는다. 하드웨어 복구 문구를 MetaMask에 입력하지 않고 하드웨어 연결 기능으로 서명한다. 하드웨어도 악성 거래를 직접 승인하면 손실을 막아 주지 못한다.

### 기존 계약에서 테스트한 토큰·대금 절차

이 절의 `withdrawProceeds`와 운영자 수동 LP 예산 집행은 **기존 버전** 설명이다. 새 100% LP 전용 판매에 적용하지 않는다.

1. 실판매 주소/조건과 signer 구성을 확정하고 **Base 메인넷인지** 확인한다. Sepolia tSOULI·판매 주소를 실판매에 재사용하지 않는다.
2. 원본 보관 지갑에서 **판매 회차 물량만** 판매 운영 Safe로 보낸다. 현재 `deposit`은 owner의 잔액에서만 가져오므로 이 절차가 코드와 맞는다. 원본 지갑을 owner로 지정해 직접 입고할 수도 있으나 큰 보관 지갑을 반복 운영하는 방식은 권하지 않는다.
3. 운영 Safe가 SOULI에 대해 판매 계약 앞으로 정확한 수량을 `approve`, 이어 `deposit`한다. 무제한 사용 승인은 피하고 소비 후 잔여 allowance를 확인한다.
4. 구매자는 `buy` 한 번을 승인한다. native ETH에는 ERC-20 사용 승인이 없고, 판매 계약이 ETH를 받고 SOULI를 같은 거래에서 지급한다. 운영자/서버의 개별 송금은 필요 없다.
5. treasury Safe가 `withdrawProceeds`를 승인해 계약의 판매 ETH를 받는다. 누적 매출은 유지되고 현재 계약 잔액만 줄어든다. **순이익은 비용/세금 등을 계산한 별도 개념**이다.
6. LP는 판매 계약 밖의 별도 거래다. 검토한 SOULI와 ETH/WETH 예산만 DEX에 제공한다. 초기 가격·페어/라우터 주소·슬리피지·기한·포지션 수령 주소를 확인한다. LP 토큰 또는 NFT의 통제권이 유동성 회수 권한이므로 소액 브라우저 지갑에 방치하지 않는다.
7. LP 잠금을 선택한다면 검증된 잠금 계약·해제일·수수료 수령·긴급 복구 가능 범위를 먼저 정하고 실제 증거를 공개한다. 자동 LP/LP 잠금은 **미구현**, 수익·가격 상승·무손실을 보장하지 않는다. 이후 사용자가 100% LP 방향을 선택했지만 실제 강제 계약/잠금이 구현·검증되기 전에는 현재 기능이라고 홍보하지 않는다.

## 1. 현재 구현된 일반 ETH 판매 구조

2026-10-01 구매 UI 후속: 원본 SVG와 시작 수량을 보여주는 5개 레벨 버튼, 직접 수량 입력, 별도 결제 확인 화면을 추가했다. `scripts/snapshot-purchase-levels.mjs`가 실제 Base 블록 52,022,772에서 최소 seed 전후를 확인한 값은 **1 / 21,000 / 150,000 / 500,000 / 2,500,000**이다. UI 레벨은 1–5, 실제 계약은 0–4다. vendor 소스의 임계값은 배포 계약과 달라 사용하지 않는다. 프리셋은 새 단일 원본 기준이며 기존 보유분을 차감하거나 실제 지급 후 레벨을 보장하는 추천이 아니다. `purchase-levels.json`에 extra=0인 원본 샘플·블록·해시를 보관한다. 수량 변경 시 이전 견적·동의가 초기화되고 금액·한도 검증은 유지된다. 흰 바탕·버터 노랑 버튼·파스텔 프레임을 사용하며 원본 SVG 색은 바꾸지 않는다. 소개는 Base 위의 ERC20i 씨앗/24×24 아트에 집중한다.

금고와 지갑을 구분해서 설명한다. **기존 판매 계약은 SOULI와 ETH를 보관하는 온체인 금고 역할을 한다.** 계약의 `treasury`는 ETH를 인출할 권한과 수령 지갑 주소를 지정하는 값이다. 일반 MetaMask 계정 주소도, Safe 같은 스마트 계약 지갑 주소도 지정할 수 있다. 이 기존 버전에는 별도의 자체 treasury 프로그램이 필요하지 않았다. **새 LP 전용 방향에는 자유 인출을 막는 계약 로직과 LP 잠금이 추가로 필요하다.** 테스트에서는 관리자와 treasury를 같은 MetaMask 주소로 정했지만, 앞으로의 권한은 위 후속 결정을 따른다. 메인넷 배포와 실제 주소 지정은 아직 하지 않았다.

```text
운영자 MetaMask의 SOULI
  └─ 정해진 수량만 approve → 판매 계약에 deposit

구매자 MetaMask의 Base ETH
  └─ buy(수량) 한 번 승인
       ├─ ETH: 판매 계약에 보관
       └─ SOULI: 같은 거래에서 구매자 지갑으로 지급

계약에 고정된 treasury 지갑
  └─ withdrawProceeds → 누적 판매 ETH 수령
```

구매마다 운영자가 송금하거나 서버가 개인키를 보관할 필요가 없다. Codex가 운영자의 지갑을 보관하거나 대신 코인을 임의로 판매하는 구조도 아니다. 운영자는 검토된 계약에 판매 재고만 입고하고, 구매자가 직접 계약을 호출한다. 현재는 **메인넷 입고 주소가 정해지지 않았으므로 실제 SOULI를 먼저 옮기지 않는다**. Sepolia 판매 계약에는 tSOULI만 사용한다.

결제 통화는 **Base 네트워크의 native ETH**다. Ethereum 메인넷 ETH, WETH, USDC 결제는 이 계약의 입력이 아니다. ETH가 다른 네트워크에 있다면 별도 네트워크 이동이 필요하며 이 앱이 자동 브리지를 수행하지 않는다. 구매자는 SOULI/USDC 지출 승인을 하지 않는다. 재고를 넣는 운영자만 정확한 수량의 SOULI `approve`가 필요하다.

ETH 선택은 기존 Base·MetaMask 흐름에 맞추고 첫 버전의 결제 경로를 단순하게 하기 위한 판단이다. 시장에서 가장 인기 있는 결제 통화라는 주장은 하지 않는다. USDC 결제는 별도 검증된 경로로 확장할 수 있다. Base 수수료에는 실행비와 L1 데이터 비용이 있으므로 무료나 일정 금액으로 보장하지 않는다. UI는 두 비용을 포함한 추정치를 보여주고 최종 금액은 지갑에서 확인한다.

## 2. 이번 판매 방식의 범위

SOULI 한 개의 ETH 가격을 판매 회차별로 고정한다. ETH의 달러 가치가 달라지면 SOULI 판매가의 달러 환산도 달라진다. 배포 후 가격·판매 한도·지갑별 한도·시작/종료 시각·treasury·토큰 주소·조건 해시는 바꿀 수 없다. 조건을 변경하려면 기존 회차를 닫고 새 계약과 새 명세를 검토해야 한다.

이 기존 구현은 DEX나 본딩 커브가 아니다. 구매가 누적돼도 자동 가격 인상, 거래쌍 생성, LP 적립/잠금, 원금 보장, 환매가 발생하지 않는다. 판매대금은 계약에 모이고 고정된 treasury만 인출한다. **후속 결정은 100% LP 전용 적립이며, 가격·목표·잠금 조건과 그 구현은 아직 미완료다.** 이전 USDC 계산기와 LP/환불 미리보기는 기존 개발용 시뮬레이션으로 보존하며 새 실판매 조건의 근거로 사용하지 않는다.

구매가 성공하면 즉시 SOULI가 전달되며 이후 환불 함수는 없다. 지급 실패나 조건 불일치로 거래가 되돌려지면 결제 ETH와 계약 내부 집계도 함께 되돌려진다. 실패 거래의 네트워크 수수료까지 환불되는 것은 아니다. 지갑별 한도는 주소 기준이며 한 사람이 여러 지갑을 만드는 것을 방지하지 않는다.

## 3. 기존 ERC20i와 캐릭터

- Base 토큰: `0xb43eA104c7ec75038Ac8EcA57107Eefc8B039aFF`, decimals 9.
- 기존 토큰과 SVG 생성기를 교체하지 않는다. 게임도 삭제하거나 새로 만들지 않는다.
- 판매 수량은 1 SOULI 단위의 양의 정수로 한정한다. 원본 전송 로직의 분수 seed 반올림 문제를 피하기 위한 범위 제한이다.
- 일부 구매는 구매자 Dynamic seed를 늘린다. 재고/보유 형태에 따라 Stable 원본을 전달할 수 있다. 따라서 “구매하면 반드시 새 캐릭터/특정 레벨/특정 모양”을 약속하지 않는다.
- 실제 Base 복제 테스트에서 210 구매 → Dynamic 210, 추가 10 → Dynamic 220, 나머지 780 전량 구매 → Stable 780을 확인했다.
- 운영자 지갑에서 재고를 입고하는 전송도 원본 형태에 영향을 줄 수 있다. 보존하려는 원본과 판매용 재고를 먼저 구분하고 입고 계획을 검토한다.
- Stable은 기존 계약의 저장 형태를 뜻한다. 이후 부분 출금이나 원본 계약의 아트 관리 권한과 무관하게 영원히 같은 이미지라고 보장하지 않는다.
- 기존 `pool`은 과거 설정된 주소다. 새 판매 계약을 그 주소로 변경하는 설계를 가정하지 않는다. pool 같은 특수 주소의 캐릭터 처리와 실제 구매자 보유 이력의 추가 케이스는 공개 출시 전 확인 대상이다.

구매자는 지갑에서 선택한 계정으로만 수령한다. 프런트가 임의 지급 주소를 지정하지 않는다. 계약은 정확한 ETH 금액, 잔여 재고, 누적 판매 한도, 주소별 누적 한도, 시작/종료 시각, 견적 기한을 검사한다. 전송 전후 구매자/계약의 토큰 잔액 차이도 대조한다. SOULI 지급이 실패하거나 예상과 다르면 거래 전체가 실패한다. 단순 ETH 송금과 알 수 없는 함수 호출은 거절한다.

관리자는 판매를 멈추고, 멈춘 상태에서 미판매 재고를 회수하며, 2단계로 관리자를 이전할 수 있다. 관리 포기로 재고가 고립되지 않도록 renounce는 차단했다. 판매 대금 인출은 immutable treasury에만 허용한다. treasury가 ETH 수령을 거절해도 구매 과정에서는 treasury를 호출하지 않아 SOULI 지급을 막지 않는다. 단, treasury를 잘못 정하면 인출이 어려우므로 배포 전 실제 통제·ETH 수령 능력을 확인해야 한다.

브라우저는 배포 코드 해시와 모든 핵심 조건을 읽어 검토 명세와 비교한다. URL·localStorage·원격 API가 판매 주소를 바꾸도록 하지 않았다. 계정/체인 변경, 오래된 Base 데이터, 부족한 ETH, 만료 견적은 결제를 차단한다. 전체 토큰 가격은 BigInt로 계산한다. 견적을 보여준 후 사용자 확인이 있어야 지갑 거래 요청을 띄운다.

중복 클릭과 다른 탭의 동시 구매 요청은 Web Locks와 저장된 대기 기록으로 차단한다. 거래 요청 전에 복구 정보를 기록하고 전송 hash를 즉시 저장한다. 불명확한 연결 오류는 자동 재전송하지 않는다. 새로고침 후 복구, 원래 nonce의 속도 올리기/취소, hash 수동 확인을 지원한다. 로컬 기록만 보고 성공으로 표시하지 않고 실제 거래 목적지·금액·calldata·정상 영수증·Purchased 이벤트와 블록 해시를 대조한다. UI는 2블록 확인 후 완료를 표시하며 이것이 Ethereum L1 최종 확정과 같은 뜻은 아니다.

## 6. 실제 입고와 개시 순서

1. **조건 결정:** SOULI 한 개의 ETH 가격, 총 판매량, 지갑별 한도, 기간, 계약 관리자, 대금 treasury, 매출의 운영비/LP 사용 방침을 정한다. 기존 미확정 1 USDC/14 SOULI 또는 FDV를 끌어오지 않는다. 테스트 가격도 실제 가격 제안이 아니다.
2. **검토용 파일 생성:** `release.mjs prepare`는 생성자 인자와 서명 없는 배포 calldata만 작성한다. 개인키는 입력받지 않으며 거래를 보내지 않는다.
3. **독립 계약 검토 및 테스트넷 실지갑 검증:** 실제 MetaMask의 승인/취소/네트워크 이동·연결 종료·모바일 환경, 운영 지갑의 입고·중지·재고 회수·대금 인출을 확인한다. Base Sepolia에는 실제 SOULI가 없으므로 별도 테스트 토큰이라는 표시가 필요하다. 복제 테스트 결과로 이 단계를 대체했다고 하지 않는다.
4. **사용자의 지갑으로 Base 배포:** 검토한 가격/주소를 확인한 후 사용자가 거래를 승인한다. 계약은 처음에 paused다. 가능하면 운영자/treasury를 통제 가능한 멀티시그로 정하고 역할과 복구 절차를 문서화한다.
5. **배포 결과 대조:** `release.mjs verify`로 컴파일한 런타임과 배포 코드(immutable 위치 제외)를 비교하고, 해당 immutable 값과 owner·token·조건을 별도로 검증한다. 원본 SOULI 코드 해시도 확인한다. 탐색기 소스 공개 검증을 완료한다.
6. **MetaMask로 재고 입고:** SOULI `approve(판매 계약, 정확한 수량 × 10^9)`를 승인하고 판매 계약의 `deposit(정수 SOULI 수량)`를 승인한다. 앱/계약의 입고 잔고와 보존하려는 원본을 다시 확인한다. 무제한 allowance를 기본값으로 하지 않는다.
7. **소량 확인 후 공개:** 검토된 운영 절차에 따라 unpause와 소량 실거래 확인을 진행하고, 검증된 명세를 `LIVE_SALE`에 고정한다. 실제 재고/기간/정지 상태를 확인해 수동으로 사이트를 배포한다. 운영용 판매 상태 표시도 실제 명세와 함께 갱신한다. 현재 API의 `sales:false`는 운영에서 아직 판매가 열리지 않았다는 기존 상태다.
8. **운영:** 입고 잔고·판매 event·ETH 잔고·대금 인출을 대조한다. 이상 시 pause한다. 운영자가 미판매분을 회수할 수 있다는 권한을 숨기지 않는다. 판매 종료 후 미판매 재고와 대금을 각각 처리한다.

입력 파일의 필수 키는 `chainId`(8453 숫자), `token`, `owner`, `treasury`, `unitPriceWei`, `saleCap`, `walletCap`, `startsAt`, `endsAt`다. 수량·가격·Unix 초는 소수 없는 **문자열**로 쓴다. 기본 공개 체인 검토 도구는 테스트 체인 입력을 거절한다.

```sh
# contracts 폴더에서, 사용자가 확정한 파일로만 실행
node scripts/release.mjs prepare reviewed-terms.json unsigned-deployment.json
node scripts/release.mjs verify unsigned-deployment.json SALE_ADDRESS WHOLE_STOCK verified-sale.json
```

생성된 `candidateManifest`는 배포 승인이나 판매 개시를 의미하지 않는다. 코드가 자동으로 `LIVE_SALE`을 바꾸지 않는다. `unsignedInventoryPlan`의 세 거래는 각각 approve, deposit, unpause이며 반드시 각 단계 결과를 확인한 후 진행한다.

## 7. 서버와 이후 확장

판매의 돈·재고·지급은 Base 계약이 처리한다. 사이트 호스팅과 공개 RPC는 필요하고, 협동 마을/인증/시세/서버 저장에는 기존 선택적 API가 남는다. 자동 판매를 위해 별도의 서버 서명 봇이나 지급 스케줄러를 운용하지 않는다. 현재 Google Cloud 호스팅 유지/이전 결정, Docker 실제 이미지 실행 검증, 클라우드 배포는 이번 판매 구현과 별도로 남아 있다.

본딩 커브·자동 LP·유동성 잠금·수익 배분·추가 결제 통화는 별도 경제 설계와 계약 검증이 필요하다. 현재 계약에 구현됐다고 홍보하지 않는다. 사용자의 기존 투자/운영 결정과 판매대금 사용 방침을 공개 조건으로 확정한 뒤 이어간다.
