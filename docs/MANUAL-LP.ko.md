# SOULI 수동 LP 운영 방향

## 최신 권한 변경 (2026-10-02)

사용자가 Safe를 보류하고 세 지갑 각각 단독 관리/출금을 선택했다. 아래 과거 2-of-3 계획보다 [THREE-WALLET.ko.md](THREE-WALLET.ko.md)가 우선한다. 수동 LP, 즉시 지급, 성공 구매 환불 없음, LP 사용처 계약 미강제는 동일하다.


2026-10-02 · 최신 사용자 결정 · 로컬 기획/표시 변경 · 실판매/실제 Safe 설정 아님

이 문서는 이전 LP 전용 적립·자동 Uniswap 공급·인출 불가능한 준비금 계획을 대체한다. 사용자는 게임/캐릭터 이용을 위한 즉시 SOULI 구매를 유지하고, 판매대금을 treasury로 인출한 뒤 운영자가 직접 LP를 공급하는 방식을 선택했다. 1-of-3을 검토한 뒤 **A/B/C 세 서명자 중 두 지갑이 승인하는 2-of-3**으로 최종 결정했다. 세 공개 주소를 받아 Base Sepolia 형식/잔액/공식 Safe 배포 코드 해시를 읽기로 확인했다. 실제 Safe 주소는 아직 없으며 배포/권한 변경/자금 이전은 하지 않았다. 개인 별칭은 저장소 밖의 로컬 비공개 메모에만 보관한다.

## 구매와 LP는 별도 거래다

1. 운영자가 판매할 SOULI만 판매 계약에 입고한다. LP용 SOULI는 별도 재고로 관리한다.
2. 구매자가 Base ETH로 결제하면 같은 거래에서 SOULI를 즉시 받는다. 판매 계약은 ETH를 보관한다. 토큰 지급 실패 시 결제와 집계도 되돌린다. 가스비는 별도다.
3. 지정된 treasury가 판매 계약에서 ETH를 인출한다. 인출은 LP 공급이 아니다.
4. 운영자가 treasury에서 Uniswap에 ETH/WETH와 SOULI를 공급한다. 풀 주소, 공급 거래, LP 지분 수령 주소를 공개한다.
5. LP 지분을 따로 잠그려면 별도 잠금 거래/권한 검증이 필요하다. Safe 보관만으로 잠겼다고 표시하지 않는다.

현재 이 흐름의 기반은 `contracts/src/SouliEthSale.sol`이다. `withdrawProceeds()`는 **배포 시 고정한 treasury 주소 자신만 호출**할 수 있고, 판매 계약의 ETH 전액을 그 주소로 보낸다. treasury가 Safe라면 소유자 A의 MetaMask가 직접 호출하는 대신, A가 Safe 거래를 승인하고 **Safe가 판매 계약을 호출**해야 한다. Safe 내부의 서명 기준은 판매 계약이 정하지 않는다.

판매 관리자 `owner`와 대금 수령자 `treasury`는 다른 역할이다. 같은 Safe를 둘 다 지정할 수 있지만 아직 결정/설정하지 않았다. 재고 `deposit()`은 owner의 토큰과 승인을 사용한다. 중지·재개·미판매 재고 회수는 owner 권한이고, 미판매 재고는 일시중지 후 회수한다. treasury 인출 권한은 owner 교체와 별개다. 기존 Sepolia 판매의 고정 treasury는 EOA이므로 Safe 실험은 별도 판매 배포가 필요하다.

`SouliLpSale`/`SouliPermanentLpLock`과 그 테스트는 **보존한 연구 후보**다. 현재 출시 경로로 연결하거나 자동 실행기를 추가하지 않는다. 기존 공개 Sepolia 계약과 프런트 구매 경로를 이 후보로 교체하지 않는다.

## 지갑 권한과 남은 검증

확정한 2-of-3은 A+B, A+C, B+C 중 어떤 조합이든 두 지갑의 승인이 필요하다. 한 지갑만으로 실행할 수 없다. 표준 Safe에서 두 서명자는 자금 전송뿐 아니라 소유자/승인 기준 변경도 할 수 있다. LP 사용처나 잠금을 강제하지는 않는다. 권한 있는 모듈은 일반 서명 경로를 우회할 수 있어 별도로 확인한다. [Safe 공식 권한 설명](https://docs.safe.global/advanced/smart-account-concepts)

독립 키/기기의 2-of-3을 사용한다. 같은 복구 문구에서 만든 계정 세 개는 독립 키 보관의 대체가 아니다. 게임 접속/일상 dApp용 지갑과 관리 서명 지갑을 분리한다. 실제 보유자·threshold·모듈·guard·fallback handler와 트랜잭션 목적지/금액을 공개 체인에서 확인한다. 휴대폰 지갑에서 승인하려면 해당 네트워크의 공개 Safe와 접근 가능한 공식 Safe 인터페이스가 필요하다. 로컬 테스트는 기기 간 실제 서명 검증을 대신하지 않는다.

다음 실험은 별도 Sepolia Safe를 사용하는 판매 재고 입고 → 다른 구매자 구매 → Safe 대금 인출 → 수동 LP 공급 → LP 소유권 확인이다. 기존 테스트는 구매자/owner/treasury가 같은 EOA였다. 실제 Safe 연동을 검증했다고 표현하지 않는다. 선택한 승인 수와 다른 수량으로 서명했을 때, 잘못된 treasury에서 호출했을 때, LP 공급 실패/슬리피지 초과 시를 포함한다. 공개 메인넷 자금은 사용하지 않는다.

## 웹에 보여줄 값

| 표시 | 근거와 의미 |
|---|---|
| SOULI sold | 판매 계약 `sold`와 확정 `Purchased` 이벤트. 판매가/총량/실제 체인 표시 |
| Total purchase ETH | `proceedsWei`와 구매 이벤트. 인출해도 줄지 않는 누적 매출이며 이익이 아님 |
| ETH in sale contract | 해당 블록의 현재 ETH 잔액. 강제 입금은 매출과 다를 수 있음 |
| ETH in treasury | 공개한 전용 treasury의 현재 잔액. 구매 매출, 창업자 보충, 기타 입금을 구분 |
| ETH added to LP | 공개한 공급 거래에서 실제 사용된 ETH/WETH만 집계. 누적 투입금이며 현재 풀 잔액과 다름 |
| LP ownership / lock | LP 소유 주소, 실제 보유량, 회수 권한, 검증된 잠금 조건/종료일. 미확인 시 미확인 표시 |

실판매 주소/목표/증거가 없는 지금은 `— / Not configured`로 표시한다. 기존 testnet 수치를 mainnet 실적으로 사용하거나 임의로 `0%`/`100% funded`를 채우지 않는다. 읽기 실패를 0으로 바꾸지 않고 관측 블록·시각·지연 상태를 보여준다. 실판매 전에는 실제 조회와 이벤트 대조가 필요한 작업이다.

진행률은 **판매 목표 대비 누적 매출**과 **LP 공급 계획 대비 실제 투입**을 구별한다. treasury로의 인출을 LP 실적으로 계산하지 않는다. 창업자 보충은 별도 항목이고 매출에 더하지 않는다. 같은 ETH가 판매 → treasury → 풀로 이동할 때 중복 합산하지 않는다. LP 지분 회수/이전도 별도로 보여줘, 과거 공급량만으로 현재 자금이 남아 있는 것처럼 보이지 않게 한다. 실제 풀 잔액은 거래로 계속 변한다.

## 금액과 공개 약속

- 기존 **15M USD FDV 기준, ETH 쪽 $50k 상당 + 맞은편 SOULI**는 계산 제안으로 유지한다. 실제 ETH 목표·단가·기간·DEX 버전/주소는 아직 확정하지 않았다. USD 환산은 기준 시각을 표시한다.
- 초기 판매대금을 LP에 쓰겠다는 의도는 유지한다. 이번 요청은 운영비 전용 허가가 아니다. 다만 **기존 판매 계약은 그 사용처를 강제하지 않고 treasury는 인출/전용할 수 있다.** 운영 약속과 기술적 인출 가능성을 함께 공개한다.
- 창업자가 부족분을 보충할 수 있다. 기존 판매 계약은 직접 ETH 송금을 거절하므로, 공개한 treasury로의 별도 지원 거래로 기록한다. 이 단계에서는 공개 기부 접수나 토큰 없는 지원 결제를 열지 않는다.
- 목표 달성은 온체인 자동 실행 조건이 아니다. 운영자가 가격/비율/재고를 확인하고 수동으로 LP를 공급한다. 목표 미달 또는 공급 실패 시 토큰 보유/게임 이용은 계속되지만, LP 개설일이나 재판매를 보장하지 않는다. 재시도/일정 변경은 공개한다.
- 성공한 구매에 자동 프로토콜 환불은 없다. 게임에 쓸 수 있다는 설명만으로 토큰의 변동성이나 인출 권한을 숨기지 않는다. 별도 NFT/고정 외형 판매로 오인시키지 않는다.
- 기존 제안인 첫 판매 종료 후 DEX 안내 전환을 유지한다. 고정가 판매와 DEX 거래가 동시에 열리면 차익 거래가 가능하므로 출시 전에 가격/종료 조건을 확정한다.

Uniswap 풀 생성은 토큰 두 종류로 거래 장소를 만드는 것이며 거래소의 심사/보증을 뜻하지 않는다. 새 풀의 첫 가격은 수량 비율에 따라 정해지고, 이미 풀이 있으면 현재 비율을 확인해야 한다. LP 소유자는 지분을 이용해 유동성을 회수할 수 있다. 영구 잠금은 이번에 적용한 사실이 아니며 별도 결정/검증 대상이다. [Uniswap 공식 풀/LP 설명](https://developers.uniswap.org/docs/protocols/v2/concepts/pools)

## 이번 반영 범위

홈페이지 Receipts/FAQ를 수동 LP 계획과 운영자 권한 설명으로 변경했다. 상세 권한은 접어 두고 구매 → 잔액 확인 → 운영자 LP 공급 흐름을 먼저 보여준다. 실제 집계 연결, Safe 배포/설정, LP 거래, 실판매 개방 또는 사이트 배포는 하지 않았다. `LIVE_SALE.enabled`는 계속 `false`다. 독립 보안 검토와 실제 Safe/다른 구매자 검증은 남아 있다.
