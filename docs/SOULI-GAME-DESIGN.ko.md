## 3 SOULI가 제공할 경험

가칭 게임명은 **SOULI Little World**다. 브랜드명 변경 제안은 아니며 lighthouse.html의 게임 설명에 사용할 작업명이다. 장르는 수집형 방치 마을과 가벼운 탐험이다. 플레이어는 원본의 성장과 보존을 선택하고 수집한 주민을 마을에 배치한다. 주민은 선택한 일과에 따라 자동으로 채집·돌봄·수리·귀환을 반복한다. 기존 등대와 방어 게임 초안은 비교용 프로토타입이며 이 핵심 흐름에 맞지 않는 부분은 교체한다.

핵심 감정은 세 가지다. 내 지갑의 원본 그림이 실제로 살아 있다는 애착, 떠나 있는 동안에도 작은 일이 진행됐다는 안도감, 다른 사람과 함께 장소를 만들었다는 소속감이다. 가격 상승 여부만으로 방문 이유가 사라지는 구조를 피하려면 이 감정이 독립적으로 작동해야 한다.

초기 대상은 SOULI 기존 보유자와 코인 문화에 익숙한 가벼운 수집형 게임 이용자다. 둘째 대상은 지갑 없이 구경하러 온 도트·방치 게임 이용자다. 첫 화면에 지갑 팝업이나 매수 요구를 내보내지 않고, 무료 샘플 주민으로 마을이 변하는 모습을 먼저 보여준다.

하루 조작 목표는 2회 방문, 각 1~3분이다. 원하면 더 오래 구경하고 꾸밀 수 있지만 계속 클릭하는 사람이 생산을 압도하지 않는다. 경쟁 전투력 순위, 자산 가격 순위와 거래량 순위를 주목표로 삼지 않는다.

## 6 Dynamic 성장과 Stable 보존 수집

사용자가 설명한 진화·보존은 SOULI 고유의 수집 구조다. 이를 의도하지 않은 외형 변경 문제로만 취급하지 않는다. **새 모습을 키우는 재미와 마음에 드는 모습을 남기는 재미**를 게임의 첫 화면부터 이해할 수 있게 한다.

기존 수집 UI는 Dynamic Souli와 Stable Souli라는 이름을 사용한다. 게임에서도 이 명칭을 기본으로 삼는다. Stored는 계약의 저장형 inscription을 설명하는 기술 용어로 쓰고, Static은 일반적인 설명에만 쓴다. Stable은 스테이블코인이나 가격 안정의 의미가 아니다.

| 구분 | 원본의 상태 | 플레이 경험 |
| --- | --- | --- |
| Dynamic SOULI | 보유 토큰과 전송에 따라 seed와 extra가 바뀔 수 있음 | 모으고 진화시키며 새로운 모습을 발견 |
| Stable SOULI | 보존 조건을 충족한 이전으로 seed와 extra가 저장됨 | 좋아하는 모습을 수집하고 주민으로 정착 |
| Memory portrait | 과거 모습을 기록한 비자산 초상 | 이전 모습 회상, 현재 소유권과 구분 |
| 마을 진행 | 집·행동·일지 등 게임 기록 | 원본을 재작성하지 않고 생활 경험 제공 |

제안하는 루프는 SOULI 획득 → Dynamic 관찰과 성장 → 마음에 드는 모습 선택 → 보존 조건 확인 → 사용자가 MetaMask에서 이전 승인 → 수령 지갑에서 Stable 확인 → 마을 편성 → 새 Dynamic을 다시 성장시키기다. 구매나 이전을 하지 않고도 기존 주민으로 기본 게임을 계속할 수 있다.

추가 SOULI로 성장 단계와 모습이 바뀔 수 있지만 모든 추가 매수가 단계 상승을 보장하지는 않는다. 단계는 유한하고 같은 단계에서도 형태가 달라질 수 있다. 화면의 Soul stage는 실제 배포 계약의 getSoul 또는 getMeta를 읽어 표시한다. 게임에서 얻는 Memories와 주민의 생활 경험을 온체인 진화 레벨과 혼동시키지 않는다. 획득 시점에 정해질 extra를 사전에 확정할 수 없다면 미래 모습을 정확한 결과처럼 미리 보여주지 않는다.

검토 소스는 원본 저장소 커밋 e8485db42b0aea997e7b30ce5f8b3aa352d56cf4다. trySeedTransfer의 보존 경로는 전송량의 정수 부분이 원본 seed와 일치하고, 보내는 주소와 받는 주소가 지정 pool이 아니며, 수령자가 같은 seed의 저장형 원본을 이미 갖고 있지 않을 때 현재 seed와 extra를 옮긴다. 앱은 소수점이 섞인 임의 전송을 안내하지 않고 해당 seed에 대응하는 정확한 정수 SOULI 수량을 제안한 뒤 실제 호출을 검증한다. [Souli.sol](https://github.com/yongchoi422/erc-20i-souli-smart-contract/blob/e8485db42b0aea997e7b30ce5f8b3aa352d56cf4/contracts/token/Souli.sol)

이것은 서버에서 그림을 잠그는 기능이나 기존 계약에 없는 freeze 함수를 호출하는 기능이 아니다. 실제 토큰을 사용자가 선택한 지갑으로 이전하는 행위다. 자기 지갑 간 보존 자체는 소각·유료 구매·계약상 기간 락이 아니다. 이전된 원본과 대응 토큰의 소유자는 수령 지갑이 된다.

Stored 상태는 영구 불변이나 자산 지출 면역을 뜻하지 않는다. 소스에서는 일반 출금이 동적 부분만으로 충당되지 않으면 저장형 원본을 해체해 나머지를 동적 값으로 돌리는 경로가 있다. 수령 지갑에서 토큰을 사용하거나 관리자 아트 설정이 바뀌는 경우까지 무조건 같은 그림이라고 보장하지 않는다. 같은 seed 중복, 지정 pool, 컨트랙트 자신, 0번 주소, 자기 자신에게 보내기와 잔액 부족도 검증한다. [Generator.sol](https://github.com/yongchoi422/erc-20i-souli-smart-contract/blob/e8485db42b0aea997e7b30ce5f8b3aa352d56cf4/contracts/Generator.sol)

보존 화면에는 현재 원본을 크게 보여주고 From, To, SOULI to move, Network fee, Recipient owns this soul after transfer를 표시한다. 최신 원본·잔액·대상 중복·네트워크·호출 가능 여부를 재확인한 뒤 사용자가 MetaMask에서 승인한다. 완료는 거래가 확인됐다는 사실과 수령 지갑의 seed·extra·SVG를 대조한 결과로 판정한다. 그전에는 Preserved라고 표시하지 않는다. 취소·대기·실패는 각각 처리하며 자동 재전송하지 않는다.

진화용 지갑, 보존용 지갑, 상품 결제 지갑은 권한과 목적을 구분해 지원한다. 앱이 새 개인키를 만들어 보관하지 않는다. 사용자는 MetaMask의 계정을 직접 선택하고, 자신의 다른 지갑을 같은 게임 계정에 연결할 때 각 지갑으로 인증한다. 소유하지 않은 주소로 보낼 수 있다는 점도 수령 주소 검토에서 드러나야 한다.

여러 Stable 주민은 수집과 배치·역할 선택의 폭을 늘린다. 초기 최대 6명 편성은 테스트값이며 계정 생산 총량 한도는 유지한다. 특정 외형이나 단계의 주민이 없다는 이유로 기본 진행을 막지 않는다. 체인에서 소유권이 이전되면 이전 계정의 활성 주민 권리도 갱신하지만, 집·구매 장식·이야기와 비자산 기록은 정책에 따라 계정에 남긴다.

현재 실제 이전 UI와 보존 검증은 구현되지 않았다. 검토 소스와 배포 bytecode의 일치를 확인하고 Base 포크에서 성장·보존·재입금·출금·중복 seed·소각·pool 경계를 검증한 뒤 실제 거래 버튼을 구현한다.

## 7 방치 생산과 역할의 규칙

기본 행동은 Choose a plan, Start chilling, Collect, Contribute 네 가지다. 기본값은 자동으로 정해져 있고 첫날에는 Start chilling과 결과 확인만으로 진행한다. 같은 작업을 계속 반복할 수 있으며, 접속하지 않았다는 이유로 주민이 죽거나 집이 파괴되지 않는다.

초기 밸런스 제안은 5분 작업 주기, 계정당 주기당 재료 6단위, 시간당 재료 72단위다. 활성 주민 수에 따라 계정의 작업 몫을 나누며 총량을 늘리지 않는다. 소수점 재료는 서버에 누적하고 표시·지급 시 정수화해 반복 청구에서 반올림 이득이 생기지 않게 한다. 첫 튜토리얼 작업만 60초로 줄이고 첫 가로등 제작에 필요한 재료를 1회 보장한다.

| 역할 | 자동 행동 | 플레이어의 선택 | 보상 차이 |
| --- | --- | --- | --- |
| Explorer | 길을 걷고 동굴에서 수집한다 | 다음에 보여줄 탐험 지역 | 수집 재료 구성과 도감 발견 |
| Guardian | 다리·등대·집을 수리한다 | 다음 공사에 기여할 대상 | 수리 연출과 공사 기여 기록 |
| Healer | 정원과 쉼터를 돌본다 | 주민의 휴식 장소와 정원 | 정원 재료 구성과 생활 이야기 |

세 역할 모두 혼자서 기본 진행이 가능하다. 특정 역할이나 캐릭터 희귀도를 구매하지 않았다는 이유로 필수 기능을 막지 않는다. 역할 변경은 무료이며 다음 작업부터 적용된다. 취소·새로고침으로 더 좋은 결과를 반복 추첨하지 못하도록 결과 기준과 jobId를 시작 시 고정한다.

기본 생산은 성공률 100%다. 드문 발견은 도감·장식 이야기에서만 발생하고 유료 확률형 뽑기는 넣지 않는다. 계정 경험치는 작업 완료당 고정량으로 주어 재료를 유료 구매하더라도 경험치가 함께 폭증하지 않게 한다. 전투를 추가한다면 무자산 손실 PvE 이벤트로 별도 검증하고, 초기 게임에는 공격·방어 장비와 강화 확률을 도입하지 않는다.

| SOULI | 외부 자산과 원본 주민의 기반 | 외부 전송·구매 등 실제 체인 활동 | 기존 토큰 규칙에 따름 |
| USDC | 출시 모금 제안과 운영 회계 기준 후보 | 외부 자산 | 게임 보상으로 지급하지 않음 |

처음부터 통화를 여러 개 노출하지 않는다. 상시 HUD에는 Memories와 현재 공사 진행률만 표시한다. 재료는 제작·기여 창을 열었을 때 보인다. Memories는 환전 가치가 없는 진행 점수임을 명시한다. 재료를 SOULI로 바꾸거나 게임 작업으로 실제 SOULI를 발행하는 경로는 초기 설계에 없다.

계정 생산 총량은 같고 날씨·작업 계획에 따라 재료 비율만 바뀐다. 시작 제안은 맑음 Supplies 60%·Glowstones 20%·Dew 20%, 고요함 50%·20%·30%, 비 40%·40%·20%다. 계획 선택은 해당 재료에 최대 10퍼센트포인트를 옮길 수 있고 다른 두 재료에서 나눠 가져온다. 각 재료 비중의 하한은 10%다. 어느 시장 국면에서도 모든 기본 재료가 공급된다.

제작은 확정 결과를 제공한다. 첫 개인 가로등은 튜토리얼 지급 재료 Supplies 8·Glowstones 4를 사용한다. 이후 장식은 작업 시간 기준 2~8시간, 집의 주요 확장은 1~3일의 자연 생산을 초깃값으로 조정한다. 오프라인 보상 한도와 함께 실제 세션으로 검증한다. 최종 가격표는 플레이테스트 전 확정하지 않는다.

온체인 원본의 성장 단계와 게임 Memories 진행도는 서로 다른 값이다. 게임 플레이로 실제 SOULI 잔액이나 원본 진화 단계를 임의로 올리지 않는다.

한 재료가 과잉일 때는 작업장 교환으로 다른 재료를 얻는다. 초기 제안은 2대1, 하루 교환량은 기본 24시간 생산량의 20% 이하로 한다. 이 수수료는 게임 재료 소모일 뿐 토큰 소각이 아니다. 필수 건물의 날씨 전용 재료 요구는 금지한다.

장기 소모처는 집 꾸미기, 공용 건물 기여, 도감 전시와 선택 가능한 리모델링이다. 재화가 누적됐다고 기존 집을 부수거나 진행을 초기화하지 않는다. 시즌에는 새로운 장식 선택을 추가하며 이전 구매물과 기본 해금은 유지한다.

## 9 수집 흐름을 보여주는 새 세계 구성

기존 배경, 등대 중심 구성, 가짜 대규모 주민, 짧은 탐험·회복·방어 순환은 초기 아이디어를 시험한 프로토타입이다. 새 게임의 고정 조건으로 두지 않는다. 원본 SVG와 계약·지갑 조회 기반을 재사용하면서 공간과 규칙은 새 기획에 맞춰 재구성한다.

새 세계는 **성장하는 원본을 보는 곳, 보존한 주민이 사는 곳, 주민들이 일하는 곳**을 한눈에 구분할 수 있어야 한다. 기본 카메라는 내 주민과 생활 공간에 머물고, 층이나 지역의 크기는 수집 흐름을 이해한 뒤 늘린다.

| 공간 | 역할 | 핵심 화면과 행동 |
| --- | --- | --- |
| Growing grove | Dynamic 성장의 중심 | 큰 원본 초상·현재 단계·체인 상태를 확인 |
| Soul gallery | Stable 수집과 보존 안내 | 수집한 원본을 고르고 이전 전후 상태를 확인 |
| Little town | 주민의 집과 배치 | 소유한 주민을 정착시키고 집·정원을 꾸밈 |
| Workshop | 재료 제작과 별도 상품 | 게임 재료와 실제 결제를 명확히 구분 |
| Exploration paths | 방치 작업과 발견 | 시장 날씨에 반응하는 작업 장면과 귀환 |

하늘·지상·뿌리·수정·심연은 확장할 수 있는 지역 아이디어로 남긴다. 현재의 지형, 등대 실루엣, 화면 배치나 다섯 층을 한 화면에 모두 넣는 방식까지 유지할 의무는 없다. 새 배경을 평가할 때는 내 원본이 잘 보이는지, 성장·보존·정착 동선이 이해되는지, 화면이 단순한지를 기준으로 한다.

첫 시각 프로토타입은 성장 공간, Stable 갤러리, 주민 집 3채와 짧은 수정 채집 경로로 구성한다. 공개 원본은 샘플 모드로 보여주고, 보존 이전 자체를 가짜 성공 거래로 연출하지 않는다. 등대·가로등은 실제 플레이에 어울릴 때 선택할 수 있는 공동 건축 소재다.

첫 플레이 구간은 무료 원본 관찰, Dynamic과 Stable 설명, 내 지갑 원본 보기, 정착과 짧은 작업, 작은 생활 공간의 변화까지다. 실제 매수나 보존 전송은 필수 튜토리얼이 아니다. 완성되지 않은 성장·보존·공동 기능은 현재 제공 기능처럼 안내하지 않는다.

렌더러 선택은 기존 SVG 배경을 고집하지 않고 Vue UI와 Canvas·WebGL 세계 레이어를 비교해 정한다. 다만 프레임워크 교체부터 시작하지 않고 새 장면의 원본 가독성과 기기 성능을 먼저 측정한다. 이전 프로토타입은 Git 기록으로 남기고 새 화면이 준비된 뒤 진입 화면을 교체한다.

## 10 오프라인 진행과 복귀 화면

현재 2시간 로컬 한도는 기존 구현이다. 서버형 제안은 모든 이용자에게 기본 12시간의 같은 생산 한도를 제공하고, 접속을 계속 유지해도 같은 시간당 총량을 적용하는 것이다. 한도 연장을 최초 과금 상품으로 만들지 않는다. 하루 한 번 방문하는 이용자의 손실감이 크면 24시간을 비교 실험한다.

서버는 마지막 정산 시각, 현재 계획, 소유권 유효 구간, 작업 규칙 버전을 이용해 보상을 계산한다. 매초 모든 주민을 실행하지 않고 필요할 때 경과 시간을 계산한다. 작업 중 계획 변경은 이미 시작한 구간의 결과를 바꾸지 않는다. 같은 claimId는 한 번만 지급하며 여러 기기에서 동시에 받아도 중복 지급되지 않는다.

오프라인 시간의 날씨는 서버가 보관한 당시의 regimeId와 작업 구간을 사용한다. 현재 가격을 과거 전체 시간에 소급 적용하지 않는다. 당시 날씨 기록이 없거나 데이터가 중단된 구간은 기본 비율로 계산하며 이용자에게 데이터 문제로 불리한 총 생산량을 주지 않는다.

복귀 카드의 최대 정보는 아래 세 가지다.

1. 내 주민이 한 일과 받은 재료.

2. 내 집이나 공사에서 달라진 장면.

3. 지금 선택할 수 있는 다음 행동 하나.

예시: “Your SOULI found 18 Glowstones.”, “The eastern path has a new lantern.”, “Choose tomorrow’s plan.” 숫자는 서버 정산 결과에서 가져오며 예시 문구의 18을 고정 보상으로 구현하지 않는다. 이미 본 복귀 사건은 다시 완료한 것처럼 반복 재생하지 않는다.

## 11 BTC 날씨와 실시간 연출

초기에는 BTC의 달러 가격을 기준으로 하며 “전체 코인 시장”이라고 확대 해석하지 않는다. BTC 등락만으로 전체 시장이 붉다는 것을 검증할 수 없기 때문이다. 전체 시장 표현을 쓰려면 이후 별도의 시가총액 지표와 구성·출처·갱신 간격을 추가해야 한다.

가격을 보여주는 시간과 게임을 계산하는 시간을 분리한다.

| 층위 | 제안 주기 | 목적 |
| --- | --- | --- |
| 원천 조회 | 서버에서 60초마다 | BTC 가격·24시간 변화·원천 시각 수집 |
| 화면 표시 | 새 유효 데이터 도착 시 | 작은 시장 배지와 출처 시각 갱신 |
| 분위기 판정 | 5분마다 | 비·안개·햇빛의 안정적인 변화 |
| 날씨 최소 유지 | 15분 | 오르락내리락하며 화면이 깜빡이는 문제 방지 |
| 작업 결과 | 5분 주기 시작 시 고정 | 진행 중인 보상을 갑자기 변경하지 않음 |
| 긴 이야기 묶음 | 6시간 | 같은 날씨 안에서도 사건·활동 다양화 |

CoinGecko의 simple price API는 24시간 변화율과 last_updated_at을 받을 수 있다. 데이터 제공 상품의 실제 갱신 빈도·쿼터·재배포 조건을 확인해 요금제에 맞춰 조회한다. 이용자 브라우저가 각각 외부 API를 호출하지 않고 서버 캐시를 공유한다. [CoinGecko API 문서](https://docs.coingecko.com/reference/simple-price)

초기 판정안은 USD 기준 24시간 변화율 r이다. 중립에서 r이 +1.0% 이상이면 Sunlit, -1.0% 이하면 Rainy로 진입한다. Sunlit은 +0.5% 아래에서, Rainy는 -0.5% 위에서 중립으로 돌아갈 후보가 된다. 새 상태는 두 번의 연속 5분 판정과 최소 유지 시간을 통과한 뒤 적용한다. 반대쪽 진입 문턱을 통과하면 반대 날씨를 후보로 한다. 절댓값 5% 이상은 기존 상태 안의 강한 바람·빗소리 변형으로만 표현한다. 수치는 백테스트 후 조정한다.

실시간이라는 말은 틱마다 즉각 반응한다는 뜻으로 쓰지 않는다. UI에는 “BTC weather · Updated 1m ago”처럼 범위와 시각을 보여준다. 지역 일몰은 이용자 기기 시간 또는 선택한 타임존의 미적 연출이고, 시장 판정과 보상 시각은 서버 UTC로 통일한다.

소스 시간이 180초보다 오래되면 Stale, 10분 이상 유효 데이터가 없으면 Weather resting으로 전환하는 초깃값을 둔다. 비정상 가격·null 변화율·원천 시각 역행·급격한 출처 간 불일치는 이상 상태로 분류한다. 실패한 소스를 임의의 숫자로 대체하지 않는다. 가격 정보 배지를 쉬게 하고 게임 생산은 기본 비율로 이어간다. 백업 소스로 바뀌면 기준선과 변화율 계산을 섞지 않고 출처를 함께 바꾼다.

## 12 시장 상태별 이야기와 마을 사건

| 실제 조건 | 장면 | 가능한 영어 문장 | 필요한 증거 |
| --- | --- | --- | --- |
| BTC 24시간 하락과 Rainy 판정 | 빗속 수정 채집 | “BTC is down. The cave still glows.” | 유효 BTC snapshot과 날씨 판정 |
| 하락 중 실제 공동 가로등 완공 | 비와 따뜻한 새 불빛 | “BTC red. Our little town got brighter.” | 시장 기록·공동 공사 완료·처음 보는 사건 |
| 전체 시장 지표 하락과 실제 공동 완공 | 마을 골목 확대 | “Market red. Our little town got brighter.” | 별도 전체 시장 지표까지 검증될 때 |
| 상승 중 하늘 탐사 완료 | 구름이 열리고 관측대가 켜짐 | “BTC is up. A little soul found a new path.” | 상승 판정과 해당 탐사 완료 |
| 횡보와 정원 작업 완료 | 조용한 물주기 | “A quiet market. A busy little garden.” | 중립 판정과 정원 결과 |
| 가격 데이터 중단 | 고요한 기본 배경 | “The weather is resting. Your SOULI is still at work.” | 피드 중단 상태 |
| 개인 완공만 발생 | 내 집 앞 새 조명 | “Your SOULI brought a little more light home.” | 개인 건축 완료 |
| 다른 참여자 기여 확인 | 등대 수리 동선 | “Other residents helped repair the lighthouse.” | 실제 타 계정의 확정 기여 로그 |

사용자가 제안한 문장의 방향은 이 게임의 핵심 장면으로 채택할 가치가 높다. 다만 BTC 데이터만 연결한 첫 버전에서는 “BTC red”가 더 정확하다. “Market red” 원문은 전체 시장 지표 연결 이후 사용하거나, 실제 전체 시장 상태를 표현하지 않는 별도 브랜드 문구로 명확히 구분한다.

문장은 확인 가능한 사실을 조합한 템플릿으로 먼저 만든다. 입력은 marketSnapshotId, regimeId, playerEventId, communityProjectId, completedAt, contributorCount, sourceMode다. sourceMode는 live, practice, stale을 구분한다. Practice에서는 “In this preview, residents repaired the lighthouse.”처럼 모드가 드러나야 한다.

사건 우선순위는 실제 완공, 첫 발견, 개인 작업 결과, 시장 변화 순이다. 화면에 동시에 한 문장만 표시하고 6~8초 뒤 접는다. 동일 사건은 한 번, 시장 단독 문장은 최소 30분 간격, 복귀 요약은 최대 3건으로 제한한다. 자세한 내역은 Journal에서 본다. 토스트가 결제 버튼을 가리거나 매수 행동을 권유하지 않는다.

AI 문장 생성은 필수가 아니다. 추후 도입하더라도 검증된 사건 묶음으로 표현만 바꾸고 수치·참여자·가격 전망을 생성하게 하지 않는다. 실패하면 승인된 템플릿으로 돌아간다. 플레이어 지갑 주소나 비공개 계정 정보를 외부 문장 생성 서비스에 보낼 필요가 없다.

## 13 공동 마을과 멀티플레이

첫 멀티플레이는 **비동기 공동 건축**이다. 모두가 같은 등대의 진행률을 보고 각자 재료를 기여한다. 실시간 자유 이동 채팅 MMO는 장기 선택사항이다. 같은 날씨를 본다는 사실만으로 멀티플레이가 구현됐다고 부르지 않는다.

공사 흐름은 제안 게시, 목표 공개, 재료 기여, 서버 집계, 완공, 새 장면 배포의 순서다. 목표량은 공사 시작 전 최근 참여 가능한 계정과 예상 작업량을 기준으로 정한다. 진행 도중 목표를 몰래 높이지 않는다. 출발점은 예상 유효 일일 기여량의 2일분으로 잡고, 소수 인원 테스트에서 실제 완공 시간을 확인한다.

기여마다 계정 재료 차감과 공사 증가를 하나의 DB 트랜잭션으로 처리한다. 마지막 기여가 목표를 넘으면 필요한 양만 차감하거나 남은 양을 명확히 반환한다. 동시 완공은 한 번만 발생한다. 공사가 끝난 후 참여하지 못한 주민도 완성된 공간을 즐기고, 기여자는 Journal에 자신의 기록을 남긴다.

주민 수·온라인 수·누적 주소 수·기여 계정 수는 서로 다른 지표다. 실제 100,000명이 접속하지 않았다면 “100,000 players online” 같은 문구를 쓰지 않는다. 화면에는 내 주민을 우선 표시하고 다른 참여자의 대표 행동은 구역별 제한 수만 재현한다. 이것은 실제 위치 동기화가 아니라 확인된 행동의 재연임을 설명한다.

초기에는 공개 자유 채팅을 제외하고 준비된 이모트와 공사 기여만 제공한다. 닉네임·집 이름을 받는 시점부터 길이 제한, 신고, 필터와 운영자 처리 기록을 갖춘다. 실시간 방문을 추가할 때는 인스턴스·구역·재접속 프로토콜과 운영 비용을 별도 검증한다.

## 14 원본 SVG를 살리는 2D 미술

**2D가 적합하다.** 원본의 24×24 픽셀 형태를 보존하면서 배경과 조명을 조절하는 것이 SOULI의 식별성을 가장 직접적으로 살린다. 주인공을 배경의 한 점으로 보이게 만드는 현재 축소감은 줄이고, 원본의 색을 바꾸는 대신 주변의 대비와 밀도를 조절한다.

| 요소 | 초기 미술 규칙 | 확인 기준 |
| --- | --- | --- |
| 원본 캐릭터 | 체인 SVG의 몸·눈·효과 색과 형태 보존 | 원본 비교에서 형질이 달라지지 않음 |
| 화면 크기 | 기본 72px, 작은 화면 48px, 선택 초상 96~144px | 24px 원본의 정수 배율을 기본으로 |
| 배경 | 인접 지형의 채도와 세부 묘사를 낮춤 | 밝고 어두운 원본 모두 즉시 찾을 수 있음 |
| 선택 표시 | 발밑 링·작은 이름표·옅은 뒤쪽 조명 | 원본 픽셀을 덮지 않음 |
| 전경 | 주민 주변 가림 오브젝트는 투명도 낮춤 | 눈과 몸이 지속적으로 가려지지 않음 |
| 애니메이션 | 이동·2~3px 상하 움직임·도구 오버레이 | 몸을 재도색하거나 심하게 변형하지 않음 |
| 글꼴 | 짧은 제목은 픽셀, 긴 설명은 읽기 쉬운 폰트 | 작은 화면에서 설명을 읽을 수 있음 |
| 비와 안개 | 캐릭터 레이어 앞 효과는 제한 | 폭우에서도 주민과 버튼을 구분 가능 |

팔레트 시작안은 UI 크림 #F2EEDB, 글자 #243D36, 주요 버튼 금색 #E8C974다. 하늘은 #748DA8와 #C9DADE, 지상은 #4D6859와 #82906C, 뿌리는 #4C4357와 #78856D, 수정은 #252B46와 #769DAA, 심연은 #25222D와 #AA6856를 사용한다. 이것은 배경용 팔레트 제안이며 원본 SOULI 색을 이 색상으로 강제 변환하지 않는다.

큰 공통 배경을 어둡게 덮는 한 장의 필터보다 지역별 명도 단계, 먼 배경의 대비 감소, 주민 발밑의 평평한 공간을 우선 적용한다. 수정·용암의 고채도 발광 면적은 화면의 작은 부분에 한정한다. 반짝이는 원본 효과와 배경 효과가 경쟁하면 배경 효과를 줄인다.

현재 artForStage의 배경 제거는 알려진 원본 배경 도형에 한정한다. 일반 SVG에서 비슷한 색 도형을 무작정 지우지 않는다. 원본 전체 보기와 무대용 보기의 차이를 비교할 수 있게 하고, 원본 자체는 별도 보관한다.

검증판은 공개 샘플 6개와 다양한 실제 색 조합을 지상 낮·지상 밤·비·수정·심연 위에서 비교한다. 360px·390px 모바일과 1280px 이상 데스크톱에서 내 주민을 2초 안에 찾는지 관찰한다. 정상 보기의 주민 수는 모바일 약 12명·데스크톱 약 24명부터 시작하며, 측정 결과에 따라 조절한다. 세계 전체 보기에서는 주민을 점이나 집계로 줄이고 선택한 내 주민은 계속 강조한다.

## 15 화면과 접근성

기본 화면은 세계가 높이의 약 75~85%를 차지하도록 검토한다. 상단에는 SOULI, World, My Souls, 작은 시장 배지만 두고, 하단에는 선택 주민과 기본 행동 하나를 둔다. Buy·상품·재화·랭킹·공지 카드를 동시에 펼치지 않는다.

데스크톱은 드래그와 휠 확대를 지원하고 모바일은 드래그와 확대 버튼을 제공한다. 조작 버튼의 터치 영역은 최소 44px을 목표로 한다. 키보드만으로 주요 행동과 지역 이동을 할 수 있어야 하며 포커스 표시가 보인다. 움직임 줄이기, 날씨 효과 줄이기, 음소거를 제공한다. 가격 상승·하락은 색 이외에 아이콘과 텍스트로도 구분한다.

계정과 금융 행동은 MetaMask 중심으로 연결한다. 무료 체험은 지갑 없이 가능하고, 정착 인증·보존 이전·상품 결제는 서로 구분된 지갑 요청으로 제공한다. 카드 결제나 일반 비밀번호 계정을 필수 경로로 만들지 않는다.

처음부터 모바일 세로 화면을 기준으로 작업한다. 좁은 화면에서는 상단 링크를 접고 My Souls를 하단 시트로 연다. 모달을 여러 겹 띄우지 않으며 지갑 요청은 명시적인 연결·인증·결제 행동에서만 시작한다.

초기 영어 메뉴는 World, My Souls, Journal, Workshop, Settings다. 상점은 Workshop 안에서 찾아갈 수 있게 하고 수익화 실험 전에는 숨긴다. 가격 상세에는 출처와 마지막 갱신 시간을 제공하지만 세계 위에 거래소 차트를 상시 띄우지 않는다.

## 16 과금의 목적과 상품 구성

사용자 확인에 따라 **무료 체험과 SOULI 보유자 정착**을 기본 모델로 한다. 무료 체험은 게임을 이해하고 첫 변화를 경험할 만큼 충분해야 한다. 정착 이후 추가 구매가 없어도 기본 지역과 공사를 계속 즐길 수 있다.

과금의 목적은 두 가지다. 원본 SOULI를 가지고 이 세계에 살고 싶은 이유를 만드는 것, 그리고 운영에 필요한 실제 매출을 만드는 것이다. 시장에서 토큰을 사는 행위와 운영사가 게임 상품을 판매하는 행위는 회계상 다르다. 전자는 판매 상대방에게 대가가 가고, 후자는 운영사의 매출이 된다. 운영사가 판매 상대방일 때는 보유 재고의 매각이라는 사실도 별도로 공시한다.

| 상품 후보 | 제공 가치 | 가격 실험 범위 | 제안 시점 |
| --- | --- | --- | --- |
| 무료 체험 | 공개 원본 샘플과 첫 개인 가로등 | 무료 | 첫 검증판 |
| 홀더 정착 | 현재 소유한 원본 SVG를 주민으로 사용 | 보유 인증 자체 추가 수수료 없음 | 인증 서버 이후 |
| 집 장식 묶음 | 집·정원·가로등의 선택 가능한 외관 | 3~8 USD 상당 | 실제 이용 유지 확인 후 |
| 계절 이야기와 장식 | 약 6주 콘텐츠 묶음, 구매 후 기간 내 몰아서 플레이 가능 | 8~12 USD 상당 | 콘텐츠 제작 속도 검증 후 |
| 후원자 꾸미기 | 명패·우편함·전시 프레임 | 5~10 USD 상당 | 권리·기간 명시 후 |
| 새 지역 확장팩 | 별도 이야기·꾸미기 공간 | 10~20 USD 상당 | 기본 다섯 층 완성 이후 |

모든 가격은 시장 검증 전 제안이고 현재 SOULI 환산 가격이 아니다. 첫 유료 실험은 장식 묶음 한 종류로 제한한다. 자동 갱신 구독은 처음부터 넣지 않고 상품 제공 의무와 취소·환불 절차를 갖춘 뒤 검토한다.

유료 상품으로 토큰 수익률, 희귀 주민 당첨 확률, 무한 생산력, 다른 이용자의 손실을 판매하지 않는다. 추가 원본 수집은 외형과 편성의 다양성으로 연결하고, 게임이 임의로 생성한 새 NFT를 원본 SOULI인 것처럼 판매하지 않는다. 구매 장식은 계정 귀속의 이용 권리이며 NFT인지 여부를 혼동시키지 않는다.

장식과 이야기가 매력적이지 않아 구매가 발생하지 않는다면 토큰 의무 결제만으로 사업이 지속되지는 않는다. 상품을 사지 않은 이용자가 게임을 계속 좋아할 수 있어야 보유와 입소문도 유지된다.

## 17 SOULI 결제와 USD 기준 가격

장기적으로 SOULI를 게임 상품 결제에 사용할 수 있게 하는 것은 브랜드와 자산의 쓰임을 연결한다. 하지만 **SOULI를 반드시 먼저 사게 한다는 사실만으로 지속적인 가격 상승이 만들어지지는 않는다.** 매입한 토큰이 운영비 마련을 위해 다시 팔리면 그 경로까지 함께 봐야 한다.

권장안은 상품의 기준 가격을 USD 상당으로 정하고 첫 결제는 MetaMask가 승인하는 Base USDC 온체인 거래로 검토하는 것이다. USD는 가격을 이해하기 위한 표시 기준이고 신용카드나 법정화폐 결제 방식이 아니다. 원본 보호와 실제 시세가 검증된 이후 SOULI 지불도 선택할 수 있게 한다. SOULI 결제에서는 수량을 한정된 시간 동안 견적한다. 토큰 가격이 10배 올랐다는 이유로 같은 장식의 달러 비용이 10배 오르지 않게 한다. 견적은 토큰 최소 단위로 올림·내림 규칙을 명시하고 약 60초의 유효기간을 둔다. 시세가 오래됐거나 유동성이 부족하면 결제를 중지한다.

최초 유료 출시의 경로는 두 후보를 비교한다.

| 경로 | 장점 | 해결할 문제 | 권고 |
| --- | --- | --- | --- |
| SOULI 지불 | 사용 수요가 명확함 | 캐릭터 외형 변화·시세·유동성·정산 위험 | 외형 보호와 가격 검증을 통과한 뒤 |
| USDC 지불 | 운영비 기준과 결제 가격이 안정적, 전시 원본의 SOULI를 지출하지 않음 | 직접 SOULI 매입을 발생시키지 않음, 별도 결제 개발 필요 | 첫 상품 결제의 우선 검토안 |

UI에서 SOULI가 부족하면 외부 거래 경로와 필요한 수량을 보여줄 수 있지만 자동 스왑을 몰래 실행하지 않는다. 구매 경로와 상품 결제는 각각 예상 비용·최소 수령량·가스·지출 한도를 설명해야 한다. 무제한 승인과 백그라운드 자동 매매는 기본값으로 사용하지 않는다. 지갑 연결·소유 인증·토큰 지출은 서로 다른 행동이다.

원본 보호 대안은 전시용 보유 지갑에서 SOULI를 움직이지 않고 별도의 결제 지갑에 외부 자금으로 결제용 SOULI를 마련하는 것이다. 이는 사용자 선택이며 운영사가 자산을 수탁하는 구조가 아니다. 전시 지갑에서 결제 지갑으로 옮기는 순간에도 외형이 바뀔 수 있으므로 그 이동을 안전한 방법이라고 안내하지 않는다. 두 지갑 연결은 각각 소유 인증이 필요하고 사용성이 복잡해지는 만큼 실제 테스트가 필요하다.

성장용 SOULI는 Dynamic 진화에, 보존된 SOULI는 Stable 수집에 쓰인다. 상품 판매와 홀더 정착을 분리하면 MetaMask에서 USDC로 장식을 사더라도 원본 주민의 성장과 보유에는 SOULI가 필요하다. SOULI의 수요는 정착과 소유 경험에서 만들고, 운영 현금은 실제 상품 가치에서 마련한다. 결제를 출시하기 위해 사용자에게 복잡한 지갑 분리 절차를 강요하지 않는다.

## 18 기존 판매와 보유 물량에 대한 전제

사용자는 현재까지 개인 투자자에게 약 **60,000~70,000 USD 상당의 SOULI를 판매했고 나머지 물량은 본인이 보유**한다고 설명했다. 사용자는 해당 판매대금을 전액 사용했다고 추가로 설명했다. 따라서 이 자금의 가용 잔액은 계획상 0이다. 판매 규모·분포는 사용자 제공 추정치이며 이번 작업에서 입금 원장·판매 수량·약정·전체 보유 지갑으로 대조하지 않았다. 추가 개인 자금이나 외부 운영자금은 미확인이다. 기존 구매자는 친구인 엔젤 투자자들이고 자금 사용처나 팀 토큰 잠금에 관한 약속은 없었다고 사용자가 설명했다. 관계를 관리할 수 있다는 설명은 향후 조건 변경에 대한 투자자의 동의나 새 수익 약속으로 해석하지 않는다.

판매액은 현금·USDC 현재 잔액이나 LP 규모와 같지 않다. 과거 판매 단가가 이번 고정가 제안과 같다는 정보도 없다. 따라서 60,000~70,000에 14를 곱해 판매 물량을 확정하거나, 나머지를 모두 즉시 이동 가능한 무제한 재고로 보지 않는다.

먼저 다음 공급 표를 실제 지갑·거래·약정으로 채운다. 총합은 관측 totalSupply와 맞아야 하며 동일 토큰을 LP·운영·팀 물량으로 중복 집계하지 않는다.

| 구분 | 현재 필요한 자료 | 아직 확정할 수 없는 것 |
| --- | --- | --- |
| 기존 구매자 보유 | 판매 수량·단가·날짜·잔액, 미인도 약정 | 투자자 실제 보유 비중 |
| 창업자 보유 | 소유 지갑 목록과 각 잔액 | 정확한 집중도 |
| LP 투입 재고 | 검증된 풀과 잠금 계약, 입출금 이력 | 실제 거래 가능한 유동성 |
| 약정된 물량 | 투자자 계약·팀 보상·지원 약정 | 자유 배분 가능한 잔여량 |
| 기존 판매대금 | 사용자 설명상 전액 사용, 계획상 가용 0 | 사용 내역과 과거 약정의 관계 |
| 추가 자금 | 별도 현금·스테이블·지원 예산 유무 | 실제 신규 운영 예산 |

대부분의 잔여 물량이 한 주체에게 집중돼 있다면 새 이용자는 나중의 대량 매각 가능성을 가격에 반영할 수 있다. 게임 효용과 함께 보유 지갑 공개, 장기 귀속 계획, 예측 가능한 해제 일정이 필요하다. “나중에 생태계에 넣겠다”보다 목적별 물량과 이동 조건이 검증 가능해야 한다.

사용자 설명에 따르면 과거 판매에는 자금 사용처·팀 잠금 약속이 없었다. 따라서 기존 판매대금을 앞으로의 100% LP 제안에 소급해 포함하지 않는다. 판매 기록과 수량을 정리하고, 신규 판매를 할 경우 그 자금의 사용처와 조건을 새로 명확히 공시한다. 친구나 엔젤 투자자와의 관계도 실제 설명·약속을 기록하는 절차를 대신하지 않는다.

## 19 운영비를 토큰 매각으로 충당하는 안의 평가

**PD 권고는 운영비가 없는 사업을 가정하지 않는 것이다.** 블록체인 수수료·서버·가격 데이터·개발·아트·고객 지원에는 비용이 있다. 창업자가 무급으로 일하더라도 현금 비용과 창업자의 시간 비용을 구분해서 계산해야 한다.

창업자 보유 토큰 매각만으로 운영하면 하락장에 같은 비용을 위해 더 많은 토큰을 팔아야 한다. 이용자의 장식 구매가 새 매수로 이어져도 운영사의 정산 매각이 이를 상쇄할 수 있다. 매출과 무관하게 계속 물량이 풀리는 구조는 미래 공급 부담으로 보일 수 있다.

| 안 | 자금 흐름 | 장점 | 문제 | 판단 |
| --- | --- | --- | --- | --- |
| 모든 게임 매출도 LP로 | 운영은 창업자 추가 현금 또는 토큰 매각 | LP 정책이 단순해 보임 | 운영자금 부족과 반복 매도 | 초기 권고하지 않음 |
| 초기 판매와 게임 매출 분리 | 약정 판매대금은 LP, 게임 매출은 운영 | 제품 매출로 비용 감당 가능 | 별도 공시·회계 필요 | 기본 권고 |
| 창업자 토큰만 수시 매각 | 판매 재고로 모든 비용 충당 | 초기 결제 개발을 늦출 수 있음 | 약한 시세·얕은 풀에서 급격한 부담 | 제한된 임시 수단 |
| 별도 개발 자금과 게임 매출 | 운영 현금 확보 후 제품 수익으로 전환 | 급매 압력 줄임 | 외부 현금이나 창업자 투입 필요 | 여력이 있으면 선호 |

권장 운영 원칙은 다음과 같다.

1. 이미 약속한 초기 판매의 LP 정책을 보존한다.

2. 앞으로 발생하는 게임 상품 매출은 제공 비용·세금·환불 의무·운영 준비금에 먼저 사용한다.

3. 최소 6개월, 목표 12개월의 필수 현금 비용을 변동성이 낮은 자금으로 확보한다. USDC도 달러 현금과 완전히 같은 위험은 아니라는 점을 자금 계획에 반영한다.

4. 창업자·생태계 토큰 매각은 공개한 예산의 부족분을 메우는 제한 수단으로 두고, 실제 유동성과 약정에 맞춘 상한을 정한다.

5. 운영 준비금이 목표를 넘은 뒤에만 잉여 현금의 사용처를 검토한다. 자동 바이백이나 홀더 배당은 초기 의무로 만들지 않는다.

예를 들어 필수 현금 비용이 월 3,000 USD면 6개월 준비금은 18,000, 12개월은 36,000 USD다. 현재 기존 판매대금은 전액 사용됐고 추가 예산은 미확인이다. 따라서 이 준비금이 확보됐다고 가정하지 않는다. 별도 현금이 없으면 로컬 검증으로 범위를 제한하고, 서버 운영과 유료 출시 전에 자금 출처를 정한다.

창업자 매각 계획은 월별 현금 필요와 유동성 점검으로 사전 공개한다. 정확한 매도 시각을 예고해 거래를 유도하지 않고, 기간·최대 금액·실제 사용처·실행 후 내역을 공개한다. 긴급 매도에 의존할 정도로 준비금이 줄면 새 유료 약속과 확장을 줄이는 운영 규칙을 둔다.

## 20 토큰 수요와 매도 압력

SOULI의 토큰 설계는 새 토큰을 무한 발행하는 보상 경제보다 기존 자산의 사용과 소유 이유를 늘리는 데 초점을 둔다. 다음은 가격 상승을 보장하는 요인이 아니라 수요와 공급에 영향을 줄 수 있는 경로다.

| 설계 | 수요나 공급에 미칠 수 있는 영향 | 반대 방향의 영향 | 검증할 지표 |
| --- | --- | --- | --- |
| Dynamic 성장과 Stable 수집 | 새 모습을 키우고 기존 모습을 보존하려는 추가 보유 수요 | 성장 한도·수집 피로·처분 수요 | 원본 성장·보존·재정착·수집 유지 |
| 원본 주민 정착 | 실제 소유하고 싶은 수요 | 게임이 재미없으면 이탈 매도 | 신규 정착·30일 유지·보유 해제 |
| 집·도감·애착 | 오래 보유할 이유 | 외형이 뜻밖에 변하면 불만 | 소유권 변화 후 이탈률 |
| 유료 장식의 SOULI 결제 | 외부 자금으로 구매할 때 매수 | 운영사의 환전 매도 | 신규 자금 비율·정산 매각액 |
| 수집 가능한 원본 다양성 | 다른 원본 획득 수요 | 단순 잔액과 주민 수가 일치하지 않음 | 실제 원본 등록·활성 편성 |
| 공시된 장기 베스팅 | 예상 가능한 공급 일정 | 해제 시점의 공급 증가 | 월별 해제·시장 유동성 |
| 충분한 LP | 진입과 이탈의 거래 마찰 감소 | 새 수요 자체를 만들지는 않음 | 일정 거래액의 실행 가격 |
| 커뮤니티 완공 | 재방문·추천 증가 | 무료 이용만 증가할 수 있음 | 재방문과 실제 유료 전환 |
| 선택적 비금전 투표 | 소속감과 참여 | 지분 투표가 소수 집중될 수 있음 | 참여 계정과 편향 |

Stable로 보존하면서 대응 토큰을 계속 보유하면 재판매를 미루는 이유가 될 수 있다. 그러나 자기 지갑 간 이전 자체는 시장 매수나 소각이 아니며 언제든 처분할 수 있는 물량이 사라진 것도 아니다. 다음 Dynamic을 키우기 위해 새 자금을 쓰는 경우에만 별도의 매수 수요가 발생한다.

매입·지출·락·소각은 구분한다. 기존 홀더가 가지고 있던 토큰으로 장식을 사면 당장 새 매수는 없고 운영사가 토큰을 받는다. 운영사가 그 토큰을 팔면 매도만 발생할 수도 있다. 토큰을 금고에 보관하면 일정 기간 유통을 늦출 수 있지만 영구 소각과 다르다. 소각도 수요 감소보다 작으면 가격 상승을 만들지 못한다.

활동 유지 없이 구매량만 높이는 보상, 거래량을 부풀리는 왕복 거래, 가격 상승을 약속하는 문구는 제품 설계에 넣지 않는다. 게임의 성공 지표는 토큰 가격 자체보다 잔존 이용자·자발적 구매·운영 준비금·사용성이다. 가격과 유동성은 관찰 지표로 공개하되 보상 목표로 삼지 않는다.

## 21 토큰 흐름의 수치 모델

아래는 인과관계를 설명하는 가정 모델이다. 실제 SOULI 가격 예측·거래 전략·현재 유동성 계산이 아니다.

월 게임 지출의 USD 상당액을 G, 그 지출을 위해 외부 자금으로 새로 SOULI를 사는 비율을 a, 운영사가 받은 토큰을 그달 시장에서 매각하는 USD 상당 비율을 b, 별도 창업자 매각을 F라고 하자. 다른 홀더의 매매와 환율 변동을 제외한 **관련 순주문 압력의 근사치는 a×G − b×G − F**다. 이것은 가격 변화율이 아니며 락·보유는 매수가 아니라 공급 시점 조정이다.

| 가정 시나리오 | G | a | b | F | 관련 순주문 압력 |
| --- | --- | --- | --- | --- | --- |
| 새 구매와 운영 매각이 같음 | 10,000 USD | 70% | 70% | 0 | 0 USD |
| 추가 창업자 매각 발생 | 10,000 USD | 70% | 70% | 2,000 USD | -2,000 USD |
| 기존 잔액으로 많이 결제 | 10,000 USD | 20% | 70% | 0 | -5,000 USD |
| 준비금이 있어 일부만 정산 | 10,000 USD | 80% | 40% | 0 | +4,000 USD |

마지막 행도 나중의 정산 매각이 사라졌다는 뜻이 아니다. 미매각 토큰은 현금 준비금으로 계산하지 않는다. 이런 구조에서 “상품 매출의 몇 퍼센트를 보관하면 가격이 오른다”는 결론을 내릴 수 없다.

가격 가정 0.07 USD에서 월 3,000 USD를 충당하려면 수수료와 가격 영향을 제외하고 약 42,857 SOULI를 팔아야 한다. 가격이 0.035 USD면 약 85,714 SOULI가 필요하다. 같은 비용을 두 배 수량으로 충당하는 것이 토큰 매각만으로 운영할 때의 하락장 부담이다.

운영 매출을 USDC로 받는 대안은 직접적인 SOULI 매수 경로가 줄어드는 대신 필수 운영비 환전 매도도 줄인다. 어느 안이 보유자에게 더 좋은지는 매출·신규 자금·잔존율·유동성을 함께 보고 판단한다. “모든 과금이 SOULI 구매여야 한다”는 조건을 제품 검증보다 앞세우지 않는 이유다.

## 22 공급 배분과 생태계 금고

이미 발행된 공급의 실제 소유권을 존중하고, 전체 2억 1천만 개를 새로 배분하는 백서를 작성하지 않는다. 기존 구매자 물량과 약정분을 먼저 제외한 **자유롭게 재배치 가능한 창업자 보유분 R**에 대해서만 다음 검토안을 적용한다.

| R의 용도 | 검토 비중 | 해제·사용 조건 |
| --- | --- | --- |
| 장기 생태계 준비 | 60% | 초기 해제 0, 최소 24개월 잠금 후보 |
| 창업자와 팀 | 15% | 첫 12개월 자동 해제 0, 전체를 3~4년에 풀지 않음 |
| 제품 개발·운영 | 15% | 현금이 아님. 별도 자금 조달과 실제 예산이 확인된 경우에만 제한 사용 |
| 파트너·콘텐츠 | 5% | 검수·계약·수령자별 잠금 확인 후 지급 |
| 향후 유동성 보강 | 5% | 실제 맞은편 ETH와 검증된 LP 목적이 있는 경우 |

이 비중은 사용자 검토용 권고안이며 실행·확정된 토크노믹스가 아니다. 판매/LP 재고와 기존 외부 보유분·약정부터 제외한 R에 적용한다. 팀 첫 귀속분은 전체 공급 최대 0.1%를 12개월 유예 후 24개월에 나누는 검토안이며 나머지 해제 일정은 확정하지 않는다. 큰 물량을 36개월에 단순 해제하던 이전 안은 얕은 초기 풀에 부적절해 폐기했다. 상세 조건·계산·운영비·기존 투자자 확인은 [토크노믹스 제안](SOULI-TOKENOMICS.ko.md)을 따른다. 준비금 전체를 채굴 보상으로 풀지 않으며 금고가 새 수요나 가격 지지를 보장하지 않는다.

팀 토큰 해제와 시장 매각은 별개다. 해제된 전량을 매도할 권리만 설명하지 말고 운영 매각 정책과 관련 지갑을 함께 공시한다. 계약 잠금을 선택할 때는 이체가 ERC20i 외형에 주는 영향, 수령자·일정·취소 권한·회수 가능성을 검증한다. 문서상 락과 스마트컨트랙트상 락을 구분해 표시한다.

자금 관리에는 다중서명, 일상 운영 지갑과 장기 금고의 분리, 지출 기록을 권장한다. 권한 변경은 관리자 주소가 SVG 설정이나 토큰 기능에 미치는 영향을 확인한 후 수행한다. 이번 기획을 근거로 소유권 포기·토큰 이전·락 계약 배포를 실행하지 않는다.

초기 소각 정책은 0%를 권고한다. 검토 소스에는 0번 주소 전송 시 소각 경로가 있지만 실제 배포 계약과 캐릭터 변화·환불·회계 처리를 검증해야 한다. 외형 소실 가능성과 운영자금 부족을 감수하면서 소각부터 시작할 이유는 없다.

## 23 초기 판매와 LP의 설계

### 23.1 구매 즉시 게임, LP는 별도 조성

2026-10-02 사용자는 **SOULI 즉시 지급 + 성공 구매의 프로토콜 환불 없음 + 새 초기 판매대금 100% LP 전용**을 선택했다. `LP 성공 → 토큰 청구` 또는 `목표 미달 → 환불` 경로를 신규 판매안에 두지 않는다. 구매자는 받은 원본으로 게임에 참여하고, ETH는 목표 달성 전에도 LP 전용 계약에 남는다. 토큰 지급/대금 적립 실패 시 구매 거래 전체를 되돌리는 원자성은 유지한다. 실패 거래의 네트워크 수수료와 성공 구매의 환불은 다른 개념이다.

구매용 재고와 LP 맞은편 SOULI는 별도로 준비하고, LP용 물량을 실제로 확보한 뒤 판매를 연다. 창업자/다른 참여자의 `LP support`는 SOULI를 받는 일반 구매와 분리한다. 지원자는 그 대가로 토큰·LP 지분·개별 인출권을 자동 취득하지 않는다. 목표는 ETH 쪽 50,000 USD 상당으로 사용자가 선택했으며 판매 30,000/지원 20,000 분담은 아직 예시다. 계약에는 고정 ETH 목표를 사용하고 달러 환산은 참고로만 표시하는 안을 권장한다.

2-of-3 운영 Safe의 권한은 판매 중지·미판매 구매 재고 등으로 한정하는 안을 검증한다. **LP 전용 ETH/준비 토큰/잠긴 LP는 2명이 승인해도 임의 인출할 수 없어야 한다.** 운영비는 이 신규 초기 판매대금 외의 자금으로 마련한다. 관리자 변경·임의 호출·업그레이드를 통한 우회 경로도 같은 제한을 받아야 한다.

목표 미달 또는 복구 불가능한 생성 실패 시 자금이 무기한 LP 용도로 잠길 수 있으며, 구매자는 이미 토큰을 보유하고 게임을 할 수 있다. LP 개설/매도 경로/가격을 보장하지 않는다. 구매 전 이 조건을 짧게 표시하고 계약 기능의 환불 부재를 모든 지역의 법적 권리 부재로 설명하지 않는다. 기존 실제 홀더 게임 입장·영속 저장 검증은 별도 출시 조건이며 이 기획만으로 공개 베타가 완성된 것은 아니다.

### 23.2 목표 달성 후 Uniswap 연결과 화면

권장 상태는 `Preparing → Funding → Ready → Live`다. 구매자는 `Funding`부터 즉시 토큰을 받는다. 목표/준비 토큰 충족 시 `Ready`, 실제 공급과 LP 잠금의 성공 거래를 검증한 뒤 `Live`다. 실패 시 `Ready`에서 원인을 표시하고 재시도한다. 토큰 수령은 이 상태 전환을 기다리지 않는다.

별도 자동 실행기가 목표를 감지해 고정 규칙의 유동성 생성 거래를 호출하고, 멈추면 누구나 같은 함수를 호출할 수 있게 하는 안을 권장한다. 블록체인이 조건만으로 스스로 거래를 전송한다고 설명하지 않는다. 호출자에게 페어·가격·잠금 주소 선택권/출금권을 주지 않는다. 실행기에는 외부 자금으로 마련한 가스비만 두며, 이 경로에 상시 게임 서버는 필요하지 않다. 실행기 장애/가스 부족/체인 문제 때문에 지연될 수 있다.

UI는 기존 파랑/금색·원본 인스크립션·눌리는 버튼을 유지한다. 기본은 원본/레벨, 수량/결제, LP 준비 진행률 세 가지다. 준비 중에는 **구매 ETH·지원 ETH·목표·LP용 SOULI 준비량**을 표시하고 누적 적립 그래프를 선택 제공한다. 실제 시장이 없는 고정 판매가를 캔들 차트로 만들지 않는다. 실제 LP와 체결 데이터가 확인된 뒤 DEX Screener 링크/지원되는 공식 차트 또는 TradingView Lightweight Charts를 연결한다. 가격·거래량·갱신 시각·정확한 Base 페어를 함께 표시하고 색인 지연/거래 없음은 빈 상태로 처리한다. 차트 라이브러리와 실제 시세 공급원은 별개다. 상세 거래 화면은 펼쳐 보고 게임에는 강제로 넣지 않는다.

목표 충족 후 새 구매/지원 입금은 닫고, LP 개설 후에는 DEX 거래로 연결하는 안을 권장한다. 가격/공급량/목표/초과 입금/잔여금/잠금/수수료 정책은 판매 전에 고정·공개한다. 100%는 구매대금 원금의 LP 용도 제한이며 가스·서버·감사비를 그 원금에서 공제하지 않는다. 실제 풀에 들어간 금액과 계약에 남은 미사용액을 따로 보여주고, 잠금까지 확인되지 않은 상태를 전액 투입 완료로 표현하지 않는다.

### 23.3 출시 전 검증과 미정 사항

풀 버전과 거래쌍, 기존 pool 필드와 신규 풀의 관계, 초기 가격과 외부 거래 가격의 차이, 목표/한도, LP 소유권과 잠금 기간, 수수료 수령자, 기존 풀 선점/가격 조작/생성 실패 시 재시도 규칙을 확정한다. Base 블록 52,067,385를 복제한 로컬 포크에서 실제 SOULI와 공식 Uniswap v2의 공급·매수·매도·원본 조회·LP 회수를 통과했다. 원본 pool 주소는 변경하지 않았다. 이는 새 LP 전용/잠금 계약의 검증이나 독립 감사가 아니다.

LP 공급과 잠금은 같은 실행 안에서 검증하고, 라우터의 미사용 ETH/SOULI는 LP 용도로 보호한다. LP 락은 회수 권한을 제한하지만 가격 하한이나 손실 방지를 보장하지 않는다. 새 LP 계약·자동 실행·잠금·차트 연결은 **미구현**이다. 기존 Sepolia 즉시 지급 테스트를 이 새 구조의 검증으로 쓰지 않는다. 상세 자산 불변조건·실패 시나리오·화면 규칙은 [ETH 판매 후속 결정](ETH-SALE.ko.md)을 따른다.

### 23.4 과거 USDC 제안의 계산 예시 — 현재 판매 조건 아님

기존 제안은 총공급 210,000,000 SOULI, FDV 15,000,000 USD다. 이때 제안 단가는 1/14 USD, 1 USDC당 14 SOULI다. 아래 표는 과거 USDC 회차의 비교 계산을 보존한 것이며 새 ETH 판매 가격·목표를 정하지 않는다. 현재 시장가격·기업가치 검증 결과·가격 하한이 아니다.

| --- | --- | --- | --- | --- |
| 50,000 USDC | 700,000 | 700,000 | 1,400,000 | 100,000 USD 상당 |

| 150,000 USDC | 2,100,000 | 2,100,000 | 4,200,000 | 300,000 USD 상당 |

이 과거 예시는 신규 판매 계산이며 과거 개인 투자자의 판매액을 다시 더하지 않는다. 구매자 배분분 외에 맞은편 LP 토큰 재고가 별도로 필요함을 설명한다. 새로운 ETH 기준 수량은 확정 가격·목표로 다시 산출한다. 풀 조성 가스·감사·서버비까지 자동으로 생기는 구조가 아니다.

깊이를 이해하기 위한 단순 예시로 700,000 SOULI와 50,000 USDC의 상수곱 풀에서 수수료 없이 1,000 USDC를 매수하면 약 13,725.49 SOULI를 받고 거래 후 순간 가격은 약 4.04% 높아진다. 반대로 시작 가격으로 약 3,000 USD 상당인 42,000 SOULI를 한 번에 팔면 수령액은 약 2,830.19 USDC이고 거래 후 순간 가격은 약 11% 낮아진다. 실제 풀의 수수료·집중 유동성·차익 거래·주문 경로에 따라 결과는 달라진다. FDV가 커도 실제 풀은 얕을 수 있음을 보여주는 계산이다. [Uniswap의 풀 가격 설명](https://support.uniswap.org/hc/en-us/articles/7422670207373-How-are-token-prices-determined)

이전의 `Failed → Refundable` 및 LP 이후 수령 제안은 2026-10-02 사용자 결정으로 폐기했다. 위 예시 표를 그 옛 환불/예약 구조를 다시 도입하는 근거로 사용하지 않는다.

## 24 회계와 운영 준비금

게임 매출은 먼저 총매출, 환불·부가세 등 지급 의무, 외부 수수료, 순가용 매출로 구분한다. 그다음 실제 콘텐츠 제공비·인프라·고객 지원·인건비를 지급한다. 부가세율·회계 처리·토큰 취득 원가는 운영 법인과 판매 지역 확정 후 전문가와 정한다.

준비금이 부족할 때의 초기 정책은 순가용 매출의 최대 100%를 제품 운영과 준비금에 쓰는 것이다. 특정 비율의 무조건적인 바이백·LP 재투입을 먼저 약속하면 매출이 적을 때 서비스 제공 의무와 충돌한다.

필수 비용 12개월분이 확보되고 계속 유지되는 단계에서만 잉여 현금의 사용을 논의한다. 검토안은 잉여의 70%를 신규 콘텐츠, 20%를 추가 안전자금, 10%를 커뮤니티 사업에 쓰는 것이다. 이는 현재 확정 배분이 아니며 홀더에게 사업 수익을 분배하는 정책도 아니다. 토큰 매입을 고려할 경우 별도 목적·예산·법률 검토와 공시가 필요하다.

월별 공개 항목은 유료 이용자와 순매출의 집계, 인프라·콘텐츠·인건비의 범주별 비용, 실제 토큰 매각량, LP 변화, 준비금 개월 수, 금고 지갑과 해제 일정이다. 공개 데이터에서 개인 구매 내역·신원·개인 투자자의 비공개 약정을 노출하지 않는다.

모든 미래 게임 매출도 100% LP로 보내기로 결정한다면, 최소 6~12개월 운영자금을 외부에서 별도로 확보하는 조건을 붙여야 한다. 창업자 토큰 매각을 사실상 운영비로 사용할 경우 그 흐름을 별도 표로 공개한다. 운영비가 사라진다는 표현은 사용하지 않는다.

## 25 매출과 비용의 검증 모델

다음 수치는 사업 검토용 가정이며 클라우드 견적이나 예상 매출 약속이 아니다. 서버 비용은 MAU만으로 정해지지 않는다. 동시 접속, 호출 빈도, 데이터 크기, 지역, 이중화, 가격 데이터 요금제와 가스 후원에 따라 달라진다.

| 상용 실험 | 10,000 | 5% | 15 USD | 7,500 USD | 6,750 USD | 8,000 USD | -1,250 USD |
| 성장 가정 | 100,000 | 4% | 15 USD | 60,000 USD | 54,000 USD | 20,000 USD | +34,000 USD |

월 비용 8,000 USD, 전환율 5%, 평균 지출 15 USD, 변동비 10%라면 단순 손익분기 MAU는 약 11,852명이다. 토큰 가격 상승과 창업자 보유분 평가이익을 이 매출에 넣지 않는다. 유료 광고를 쓰면 필요한 규모가 커진다.

첫 사업 판단은 1,000명의 대규모 홀더 모집보다 30~100명의 반복 플레이에서 시작한다. 다음 방문을 원하는 사람이 적다면 과금 장치를 추가하기보다 세계와 복귀 경험을 고친다. 광고 확장은 90일 실제 회수 매출에서 지급 비용·환불을 뺀 이용자 가치를 기준으로 하고, 신규 지갑 수나 토큰 거래량만으로 광고 효율을 계산하지 않는다.

## 26 온체인 범위의 선택

게임의 모든 권위 있는 상태와 규칙을 컨트랙트에 두는 것은 가능하다. 그러나 프레임마다 움직이는 그림을 블록체인에서 렌더링하는 구조는 현실적인 목표가 아니다. 이용자 브라우저가 화면을 그리고 외부 시장 가격은 오라클 등 외부 입력으로 들어온다. 계약은 시간이 지났다고 스스로 트랜잭션을 발생시키지 않으므로 진행을 확정할 호출자나 자동 실행 서비스도 필요하다.

| 항목 | 완전 온체인 게임 로직 | 제안하는 혼합 구조 | 일반 서버 중심 |
| --- | --- | --- | --- |
| 원본 SOULI와 소유권 | Base | Base | Base 조회 가능 |
| 생산·재료·공사 규칙 | 계약에 기록하고 검증 | 서버가 계산·기록 | 서버 |
| 그림·소리·입력 | 브라우저 | 브라우저 | 브라우저 |
| 시장 가격 | 외부 오라클 필요 | 서버 가격 수집 | 서버 가격 수집 |
| 거래 비용 | 상태 변경마다 비용 | 실제 자산 거래 중심 | 체인 사용 범위에만 발생 |
| 규칙 변경 | 배포·이전·권한 설계가 중요 | 버전별 서버 규칙으로 검증 용이 | 수정 용이 |

| 최초 개발 부담 | 높음 | 중간 | 낮음 |

온체인 프레임워크인 MUD는 상태·규칙·클라이언트 동기화를 구축할 선택지다. SOULI의 현재 코드를 이 프레임워크로 전면 교체하는 작업부터 시작하지 않는다. 오프라인 계산을 몇 시간 단위의 결정적 정산으로 단순화한 작은 실험을 나중에 만들어 기술·비용·사용성을 검증할 수 있다. [MUD 공식 설명](https://mud.dev/)

권장 순서는 기존 계약의 원본·진화·보존을 정확하게 연결하고, MetaMask 기반 정착·거래 흐름을 구현하며, 필요한 Azure 기능만 추가하는 것이다. 유료 장식의 영속 권리는 최소 온체인 확장 계약을 우선 검토하고, 빠른 생활 시뮬레이션과 비동기 공사는 서버 구현과 온체인 정산을 비용·검증 가능성으로 비교한다. 완전 온체인 규칙은 작은 결정적 정산 실험으로 검증한다. 서버 사건의 해시를 체인에 저장하는 것은 기록 변경을 확인하는 보조 장치다. 원본 데이터와 실행 규칙이 공개돼 누구나 재계산할 수 없으면 “게임 전체가 온체인”이라고 홍보하지 않는다.

Base 거래에는 L2 실행과 L1 데이터 관련 비용이 있고 실제 금액은 변한다. Paymaster는 이용자 대신 누군가 가스를 지급하는 구조로 비용을 없애지 않는다. [Base 수수료 문서](https://docs.base.org/specifications/transactions/network-fees), [OpenZeppelin Paymaster 문서](https://docs.openzeppelin.com/community-contracts/paymasters)

민감도 예시로 DAU 1,000명, 하루 2회 온체인 정산, 월 30일이면 월 60,000건이다. 건당 총비용을 가정상 0.001·0.01·0.10 USD로 바꾸면 각각 60·600·6,000 USD다. 이는 현재 Base 실측 견적이 아니며 오라클·RPC·서버·인덱서 비용도 별도다. 완전 온체인 안은 예상 호출을 실제 배포 후보 계약으로 측정한 뒤 결정한다.

## 27 Azure와 블록체인 중심 구조

최신 사용자 결정에 따라 필요한 서버는 Azure를 기준으로 설계한다. MetaMask는 이용자가 계정을 선택하고 인증·자산 이전·결제를 승인하는 진입점이다. 원본의 소유권, 단계, Dynamic과 Stable 상태는 Base를 권위 있는 원천으로 삼는다. Azure의 캐시나 DB가 이를 임의로 바꾸지 않는다.

블록체인에 둘 대상은 원본과 실제 자산 거래, 검증 가능한 유료 권리와 장기 소유 상태다. 서버가 필요한 대상은 외부 가격 수집, 빠른 조회용 인덱스, 인증 세션, 스팸 방지, 게임 원장, 공동 건축 집계와 운영 관측이다. 프레임별 그림과 애니메이션은 브라우저에서 처리한다.

처음에는 기존 Vue 기반을 유지하고 작은 API와 작업 모듈부터 만든다. 가격·소유권 읽기를 중앙 캐시해 RPC 호출을 줄인다. 체인 데이터는 어느 블록을 기준으로 읽었는지 기록하며 재조직과 재조회가 가능해야 한다.

일반 게임 진행을 먼저 서버에서 검증하는 경우 그 범위를 명시한다. 게임 원장의 해시만 체인에 올렸다고 전체 게임이 온체인이라고 설명하지 않는다. 장기 소유 권리와 결제를 온체인으로 추가하더라도 신규 계약의 관리자 권한·업그레이드·회수·데이터 가용성과 비용을 별도로 검증한다.

Azure Container Apps는 HTTP와 WebSocket 등을 지원하며 컴퓨팅·요청·주변 리소스에는 비용이 발생한다. 초기 비동기 공동 건축은 폴링으로 시작하고 실시간 연결은 필요가 확인된 뒤 도입한다. [Azure ingress 문서](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview), [Azure 과금 문서](https://learn.microsoft.com/en-us/azure/container-apps/billing)

MetaMask는 브라우저 확장과 모바일 연결 조건을 별도로 다룬다. EIP6963 지갑 발견으로 여러 확장이 설치된 환경의 잘못된 지갑 선택을 줄이고, 모바일에서는 MetaMask 브라우저 또는 검증한 연결 경로를 제공한다. [MetaMask 연결 문서](https://docs.metamask.io/metamask-connect/)

이번 방향 변경은 Azure 자원 생성·비용 발생·DNS 이전·새 계약 배포를 실행했다는 뜻이 아니다. 구독·리전·예산·운영 도메인을 확인하고 수동 배포한다. 자동 배포는 추가하지 않는다.

## 28 계정과 소유권 인증

무료 체험에는 지갑 서명을 요구하지 않는다. 홀더 정착의 저장·기여·구매 단계에서 지갑 소유 인증을 요청한다. 연결된 주소를 읽는 것과 서버가 그 주소의 소유자를 확인하는 것을 분리한다.

인증은 SIWE 형식을 기준으로 도메인, URI, chainId, nonce, 발급 시각, 만료 시각과 서명을 검증한다. nonce는 한 번만 사용할 수 있고 서버 세션과 결합한다. 스마트컨트랙트 지갑도 지원 범위에서 검증할 수 있도록 ERC1271 경로를 포함한다. 서명 요청에는 “Sign in to SOULI. This does not transfer assets.”처럼 실제 동작을 정확히 설명한다. [ERC4361 표준](https://eips.ethereum.org/EIPS/eip-4361)

보유 판정은 최초 정착, 활성 주민 변경, 중요 행동, 체인 이벤트 수신 때 갱신한다. 인덱서는 로그의 blockHash와 logIndex를 저장하고 재조직 발생 시 소유권 구간을 다시 계산한다. 대기 중 소유권은 Pending verification으로 표시한다. RPC 오류로 얻지 못한 값과 실제 잔액 0을 구분한다.

활성 주민은 별도 residentProfileId를 가지고 현재 chainId·contract·owner·seed·extra·svgHash·검증 블록에 연결한다. 배열 인덱스를 영구 NFT ID로 사용하지 않는다. 동적 외형이 바뀌더라도 계정의 닉네임·집·이야기는 유지하고 새 원본을 기록한다.

MetaMask에서 여러 지갑을 연결해 성장용 Dynamic과 보존용 Stable을 같은 갤러리에서 볼 수 있도록 설계한다. 다른 지갑의 원본을 같은 계정의 주민으로 등록하려면 각각의 소유 인증이 필요하다. 현재 연결 지갑이 결제 가능한 지갑이라는 점도 별도로 표시한다.

두 기기 접속은 허용하되 생산 상태는 한 계정에 하나다. public address 조회자는 관람만 가능하고 타인의 공사 재료를 차감할 수 없다. 다중 지갑 연결과 해제는 각각 증명을 요구한다. 개인정보 삭제 요청 시 삭제할 서버 정보와 이미 공개 체인에 남아 있는 기록의 차이를 설명한다.

API 초안은 GET /world, GET /market, GET /me, POST /auth/nonce, POST /auth/verify, POST /plans, POST /claims, POST /projects/{id}/contributions다. 결제 도입 시 POST /orders/quote와 GET /orders/{id} 등을 별도 권한·상태 모델로 추가한다.

모든 변경 요청은 인증, 입력 검증, 중복 방지 키, 원자적 원장 변경과 서버 시각을 사용한다. 보상 금액을 클라이언트가 요청 본문에 넣어 결정하지 않는다. 동일 작업에 대한 재시도는 처음 결과를 반환한다. 비동기 작업은 적어도 한 번 배달될 수 있다는 전제로 중복 처리를 안전하게 한다.

주문은 Quoted → Awaiting payment → Confirming → Fulfilled로 흐르고 만료·취소·실패·환불 검토 상태를 별도로 둔다. 거래 hash만 받았다고 상품을 지급하지 않는다. 계약·체인·보낸 주소·받는 주소·금액·상품 참조와 확정 정책을 검증한다. 체인 거래 확정과 DB 상품 제공 사이에는 재시도 가능한 outbox를 사용한다.

모든 자산 수량은 정수 최소 단위로 저장한다. SOULI 9자리와 USDC 6자리를 혼동하지 않는다. 재화 원장은 감사와 정합성 확인을 위해 잔액과 분리하며, 정기적으로 합계가 일치하는지 검사한다.

| 결제 견적 조작 | 서버 서명 또는 계약 검증, 만료·금액·토큰 고정 | 다른 상품과 체인에 재사용 불가 |
| 체인 재조직 | 블록 식별·확정 정책·재검증 | 일시 관측 결과를 최종 권리로 중복 확정하지 않음 |
| 다중 계정 농장 | 계정 생산 한도·거래 불가능한 재료·이상 기여 관찰 | 부정 이용이 외부 현금 보상으로 직결되지 않음 |
| 관리자 키 탈취 | 다중서명·권한 분리·감사 기록 | 일상 운영 키로 금고 전액 이전 불가 |
| API·RPC 장애 | 캐시·회로 차단·제한된 재시도 | 장애가 무한 요청으로 확산하지 않음 |
| 데이터 삭제·손상 | 백업과 실제 복구 훈련 | 지정 복구 시간 안에 원장 복구 |
| 유료 서비스 중단 | 결제 중지와 주문 대사·환불 정책 | 돈만 받고 제공 기록이 누락되지 않음 |

보유자라는 사실만으로 한 사람임을 증명하지 못한다. 지갑 수를 늘린 이용자가 공사 기록을 독점할 수 있으므로 초기에는 가치 있는 현금성 보상이나 토큰 지분 투표를 붙이지 않는다. 강한 실명 확인을 기본 요구로 도입하지 않고, 필요성·개인정보 부담·운영 정책을 먼저 평가한다.

현재 의존성과 오래된 Dockerfile을 상용 서버 기준으로 그대로 사용하지 않는다. 보안 관련 의존성 검토, 지원되는 런타임, 비밀 관리, 요청 제한과 CSP를 배포 전 점검한다. 가스 후원에는 계정별·기간별 한도와 총예산 차단 장치를 두어 무한 호출로 준비금이 소모되지 않게 한다.

## 31 운영 품질과 장애 대응

초기 서버 베타의 목표는 월 99.5% 가용성, 일반 읽기 API의 p95 500ms 이내, 쓰기 응답 p95 1초 이내다. 이는 관측·부하 테스트 목표이며 계약상 SLA가 아니다. 외부 지갑 승인과 체인 확정 시간은 별도로 측정한다.

모바일 기준은 첫 세계 조작까지 중간급 기기와 제한된 네트워크에서 5초 이내를 목표로 한다. 현재 큰 게임 번들은 지갑·구매 모듈의 지연 로딩과 화면 밖 자산 생략으로 개선한다. 브라우저 애니메이션은 기본 30fps 이상, 배경 탭에서는 작업 렌더링을 멈추되 서버 정산은 정상 동작해야 한다.

운영 지표는 오류율·지연·DB 연결·정산 대기·지갑 검증 지연·피드 시각·주문 미제공·예산 사용률이다. 가격 정보 10분 이상 중단, 같은 주문의 중복 지급 시도, 원장 불일치와 결제 증가 대비 제공 실패는 운영 알림 대상으로 한다.

복구 목표 제안은 RPO 15분, RTO 4시간이다. 관리형 DB의 실제 기능과 비용에 맞춰 확정하고 유료 출시 전에 복구 훈련으로 확인한다. 체인 결제는 복구 후 로그를 다시 읽어 대사할 수 있게 하고, 금전 관련 원장에는 더 엄격한 보존과 재구성 경로를 갖춘다.

장애 중에는 신규 결제를 먼저 중지하고 세계 관람과 안전한 기본 생산을 가능한 범위에서 유지한다. 데이터가 없는 시간의 실제 공동 활동을 만들어내지 않는다. 종료나 장기 점검 시에는 계정의 집·장식·일지와 원본 참조를 내보낼 수 있게 한다. 원본 토큰은 사용자의 지갑에 남지만 서버형 게임이 영구 운영된다고 약속하지 않는다.

## 32 출시 지역과 이용자 권리

블록체인을 사용한다는 사실만으로 게임의 유료 서비스와 토큰 판매가 모든 지역에서 동일하게 허용되는 것은 아니다. 운영 주체, 판매 대상 국가, 연령, 결제·토큰 제공 방식과 광고 표현을 실제 출시 사양에 맞춰 검토한다.

한국 대상 서비스는 게임 등급과 유통, 획득 결과물의 환전·재매입 관련 규정을 검토해야 한다. 게임 내 재료를 현금화하지 않는 설계만으로 모든 법적 쟁점이 해결됐다고 단정하지 않는다. 국가법령정보센터에서 확인한 게임산업법 제32조는 게임 결과물의 환전·알선·재매입을 업으로 하는 행위를 규정한다. [게임산업법 제32조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1032690633)

토큰의 이름보다 이용자에게 약속하는 권리·수익 분배·광고 내용이 중요하다. 금융위원회의 2023년 토큰 증권 판단 안내도 구체적 권리의 실질을 기준으로 설명한다. 이 자료만으로 2026년의 개별 SOULI 판매를 적법 또는 증권이 아니라고 결론 내리지 않는다. 출시 시점의 법령과 계약 구조를 별도로 검토한다. [금융위원회 안내](https://fsc.go.kr/no010101/79386)

유료 출시 전에는 상품 제공 기간, 계정 귀속, 소유 토큰 매각 후 장식의 이용, 환불 기준, 거래 실패, 서비스 종료, 개인정보와 외부 데이터 제공을 설명하는 약관이 필요하다. 기존 투자자 약정과 게임 이용약관은 구분한다.

마케팅은 실제 제공 기능과 예정 기능을 구별한다. 가격 상승·원금 보장·배당·자동 수익을 약속하지 않는다. “Own your original SOULI. Give it a little place to live.”처럼 현재 제공할 수 있는 효용을 설명한다. 결제나 현금성 보상 구조를 바꾸면 검토 범위도 다시 갱신한다.

## 33 가용 판매대금이 없는 현재의 착수안

사용자 확인에 따라 기존 판매대금에서 사용할 수 있는 금액을 0으로 둔다. SOULI 잔여 토큰은 현금 예산이 아니며 현재 확인되지 않은 유동성과 가격으로 평가해 서버비를 충당할 수 있다고 계산하지 않는다.

**현재 권고는 로컬 게임 완성 → 소규모 비금전 서버 테스트 → 별도 운영 예산 확보 → 제한된 상품 출시다.** 기존 구매자가 실제로 계속 플레이하는지 확인하기 전에 추가 대규모 토큰 판매를 게임의 전제 조건으로 만들지 않는다.

| 단계 | 자금 원칙 | 가능한 일 | 진행 조건 |
| --- | --- | --- | --- |
| 지금 | 추가 서비스 지출 없이 로컬 작업 | 원본 가독성·짧은 루프·가짜 데이터로 명시한 날씨 테스트 | 기존 환경 사용 |
| 작은 온라인 테스트 | 신규 현금 지출 상한 월 150~300 USD를 검토 | 소수 계정·원장·공유 가로등·캐시된 BTC 데이터 | 실제 견적과 사용 가능한 별도 예산 확인 |
| 유료 시험 | 운영·지원·환불 의무를 포함한 예산 | 장식 1종과 주문 대사 | 최소 6개월 필수 현금 준비금과 계약 검증 |
| 확장 | 반복 게임 매출과 준비금 | 새 지역·시즌·서버 확대 | 잔존율과 원가 조건 충족 |

월 150~300 USD는 구입 지시나 확정 요금이 아닌 작은 테스트의 비용 상한 후보이며 개발 인건비·감사·법률·유료 마케팅을 포함하지 않는다. 무료 요금제와 무료 RPC에 의존하는 동안은 상용 가용성을 약속하지 않는다. 예산이 마련되지 않으면 테스트 인원과 기간을 줄이거나 로컬 검증을 계속한다.

신규 개발 자금 후보는 창업자 별도 투입, 반환 조건을 명확히 한 외부 개발 지원, 실제 납품 가능한 콘텐츠의 매출, 별도 조건을 공개한 개발 목적 자금 조달이다. 아직 제공할 수 없는 상품을 무기한 선판매해 운영하는 방식은 권고하지 않는다.

초기 판매대금 100% LP 원칙을 계속 적용하는 안은 별도 운영자금이 있을 때만 성립한다. 새로운 판매 조건을 바꾸고 싶다면 “LP와 개발비를 함께 조달하는 판매”로 목적·비율·비용·실패 시 처리를 사전에 공개해야 한다. 기존의 100% LP 문구를 유지한 채 일부를 운영비로 쓰는 설계는 채택하지 않는다. 이 문서는 새 판매 조건 변경을 확정하지 않는다.

과거 자금 사용처와 팀 잠금의 약속은 없었다는 사용자 설명을 기준으로 한다. 남은 일은 실제 판매 수량·보유 분포를 정리하고, 새로운 자금 조달의 조건을 기존 거래와 분리해 적는 것이다. 일반 게임 개발과 로컬 플레이테스트는 이 정리와 독립적으로 진행할 수 있다.

위 잔존율은 업계 평균을 인용한 수치가 아니라 초기 검토용 문턱이다. 30명의 관측으로 시장 성공을 판단하지 않는다. 최소 2개 이상의 서로 다른 코호트, 관측 기간과 표본 수를 함께 기록하고 차이가 작으면 결론을 유보한다. 토큰 가격 급등 직후의 일시적 방문을 게임 유지력으로 오인하지 않는다.

분석 이벤트 초안은 preview_started, first_job_started, first_lantern_built, wallet_auth_completed, resident_settled, return_summary_viewed, project_contributed, project_completed, item_purchased, purchase_refunded다. 이벤트마다 practice 또는 live, 규칙 버전, 계정의 익명 식별자와 발생 시각을 남긴다. 지갑 주소를 모든 분석 도구에 그대로 전송하지 않는다.

첫 실험은 시장 날씨 유무에 따른 재방문, 12시간과 24시간 오프라인 한도의 체감, 원본 크기와 배경 대비, 장식 한 종류의 실제 선택이다. 여러 경제 규칙을 동시에 바꾸지 않는다. 매출을 높이면서 잔존과 만족이 하락하면 전체 효과를 다시 평가한다.

## 35 개발 단계와 완료 조건

공수는 실제 담당자·숙련도·검수 범위가 정해지기 전의 대략적인 인주 추정이다. 한 사람이 순차 진행하면 인주에 가까운 기간이 필요하고, 계약 감사 대기·법률 검토·플레이테스트 관찰 기간은 별도다. 병렬 인력이나 마감일을 전제하지 않는다.

실제 판매·자동 LP·환불 계약·락·keeper 구현은 P5의 장식 결제와도 구분되는 별도 금융 프로젝트다. 모금·풀 조건이 미정인 상태에서 같은 일정에 포함됐다고 약속하지 않는다. 완전 온체인 게임 로직 연구도 위 MVP의 완료 조건이 아니다.

첫 개발 대상은 **큰 원본이 중심에 있는 성장 공간, Stable 갤러리, 주민이 정착하는 새 마을 장면**이다. 기존 배경과 임시 게임 규칙은 비교용으로 보관하고 새 흐름이 준비되면 교체한다. 원본 조회와 지갑 등 사용할 수 있는 기반을 재사용하며 계약 검증과 시각 프로토타입을 병행한다.

## 38 출시 준비와 중단 기준

Azure 서버 배포 전에 구독·리전·예산·API 도메인·비밀 관리·백업을 확정한다. souli.net 웹 배포는 실제 호스팅 위치와 서버 연결 경로를 확인하고 기존 배포를 되돌릴 수 있게 보관한다. 자동 배포는 추가하지 않는다. 프리뷰 URL과 공식 사이트를 혼동시키지 않고 홈과 lighthouse.html을 함께 확인한다.

서버 베타 진입 조건은 작은 온라인 테스트 예산, 인증·원장·백업, 기본 장애 안내다. 유료 진입 조건은 여기에 실제 제공 상품, 운영 주체, 비용 준비금, 주문 대사, 원본 지출 영향, 환불·지역 검토와 필요한 계약 검증을 더한다.

즉시 중단해야 할 범위는 문제에 따라 제한한다. 원장 불일치는 보상 확정을 중지하고, 금전 정합성 문제는 신규 결제를 중지한다. 가격 데이터 장애는 가격 연동만 기본 상태로 돌린다. 원본 SVG 조회가 실패하면 마지막 검증 이미지를 시각과 함께 보여주되 새 소유권을 확정하지 않는다.

베타에서 다음 문제가 반복되면 확장보다 수정이 먼저다. 첫 변화까지 이해하지 못함, 내 원본을 찾기 어려움, 하락장에서 진행이 답답함, 상품보다 토큰 가격만 보고 접속함, 운영 매각이 현금 부족을 계속 메움, 실제 활동과 연출을 혼동함이다.

장기 서비스에는 콘텐츠 소유·사용 권리, 이용자 데이터 내보내기, 종료 공지와 잔여 제공 의무의 처리 계획을 포함한다. 서버형 게임이라는 사실과 영속적인 체인 자산의 범위를 정확히 설명한다.

## 40 근거와 문서 관리

기존 구현의 기준은 저장소 HANDOFF.ko.md, SITE-RELEASE.md, src/lighthouse의 관련 소스다. 웹 저장소의 검토 시작점은 master 커밋 c51fa7c다. 계약 소스 검토 기준은 e8485db42b0aea997e7b30ce5f8b3aa352d56cf4이고, 실제 체인 읽기는 Base 블록 51,979,553에 고정했다. 소스와 배포 bytecode의 동일성, 재무 원장과 기존 약정은 아직 검증하지 않았다.

외부 기술·시장·법률 자료는 2026년 9월 30일에 확인했다. 각 절의 링크는 해당 사실을 뒷받침하며, 구체적인 게임 수치·팔레트·상품·예산·일정은 이 문서의 설계 제안이다. 실제 배포 시점에 API 조건·클라우드 가격·법률·의존성을 다시 확인한다.

사용자 제공 사실은 무료 체험과 홀더 정착의 선택, 기존 개인 판매 약 6만~7만 USD, 나머지 물량의 본인 보유, 판매대금 전액 사용, 구매자가 친구인 엔젤 투자자들이며 사용처·팀 잠금 약속이 없었다는 설명이다. 토큰 수량·정확한 소유 비중·자금 사용 내역과 투자자 약정은 아직 자료로 대조하지 않았다. 이 문서는 내부 검토용이며 공개 판매 설명서나 수익 약속으로 사용하지 않는다.

이 문서의 다음 수정은 사용자 결정, 플레이테스트, 실제 원가와 계약 검증 결과를 반영한다. 수정 시 확정된 결정을 제안으로 되돌리거나, 미정 사항을 구현된 기능으로 바꾸지 않는다. 이번 1.1 수정은 사용자 설명에 따라 기존 배경·게임 초안을 재설계 대상으로 명확히 하고 Dynamic·Stable 수집, MetaMask와 Azure, 블록체인 우선 원칙을 반영했다. 게임 코드의 실제 상태는 HANDOFF와 SITE-RELEASE에 계속 따로 기록한다.
